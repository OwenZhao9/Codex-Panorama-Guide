# 第七章：Codex App 安装与上手

这一章标题沿用读者常说的“Codex App”，但当前产品中，更准确的入口是 **ChatGPT 桌面应用里的 Codex**。同一个桌面应用可以承载 Chat、Work 和 Codex；选择 Codex 后，界面会突出本地项目、终端、文件差异、Git 和技术执行细节。

安装的目标不是把所有高级能力一次打开，而是完成一条最小闭环：从官方来源安装、登录正确账号、打开安全练习项目、使用受限权限完成任务，并亲自检查结果。

## 7.1 从官方来源安装

在 ChatGPT 官方下载页面或官方文档提供的商店链接获取桌面应用。macOS 与 Windows 的安装分发方式可能不同，企业设备还可能由管理员统一部署。

不要从第三方下载站、网盘或陌生安装包获取所谓“Codex 专版”。桌面应用会接触本地文件、账号和工具，安装来源不可信会带来比普通聊天更大的风险。

下载前重新查看当前系统要求。Windows 端官方推荐 Windows 11；较新的 Windows 10 仅提供 best effort 支持。macOS 的具体兼容范围可能随版本更新，以下载页实际提示为准。Linux 用户应使用网页、CLI 或 IDE Extension，而不是安装来源不明的桌面替代品。

安装后保持应用更新。Codex 客户端、权限实现和工具连接都会变化，旧版本可能缺少功能或出现已修复问题。在企业环境中，更新节奏可能由管理员控制，不要自行绕过管理策略。

## 7.2 第一次登录

打开应用后选择 **Continue to sign in**，在浏览器完成 ChatGPT 登录。回到应用后，先检查头像、账号和当前工作区，避免把个人材料放进组织工作区，或把组织项目放进个人账号。

也可以通过 **Sign in another way** 使用 API key，但入门阶段通常没有必要。API key 登录按 API 组织与项目计费，并且部分依赖 ChatGPT 工作区或云服务的功能不可用。Codex cloud 则要求 ChatGPT 登录。

如果使用企业或学校工作区，是否可见 Codex、模型、插件和本地功能还取决于管理员授权。登录成功只证明身份有效，不证明每个产品入口都已启用。

云端 Codex 对账号安全要求更高。使用邮箱密码登录时，应按官方要求启用多因素认证；使用 SSO 或社交登录时，遵循相应身份提供方和组织的 MFA 策略。

## 7.3 找到 Chat、Work 与 Codex

桌面应用中通常可以从产品选择器进入 ChatGPT 或 Codex。在 ChatGPT 一侧，输入区可在 Chat 与 Work 之间切换；选择 Codex 后，则进入面向项目和开发工具的界面。

第一次练习本地文件时，选择 **Codex**。如果只是问安装问题，不需要项目执行，可以使用 Chat。需要日常报告或演示，又不想看到大量技术细节时，可以选择 Work。

找不到 Codex 时依次检查：应用是否为当前版本；登录的账号和工作区是否正确；方案是否支持；组织管理员是否开放本地 Codex。不要通过反复卸载解决账号权限问题。

## 7.4 添加第一个本地项目

选择添加本地项目，然后打开上一章准备的 `codex-practice` 文件夹。项目根目录应该包含任务所需材料和输出位置，但不包含无关的个人文件。

不要为了方便选择整个 `Documents`、用户主目录或云盘根目录。项目边界越大，Codex 可见内容越多，搜索也越容易被无关材料干扰。

打开后先确认界面显示的项目名和路径。Windows 用户还要注意项目究竟位于 Windows 文件系统还是 WSL；本地代理与项目工具应尽量处于同一环境，避免路径、权限和性能混乱。

Git 仓库可以选择直接在当前项目运行，也可以使用 worktree 隔离修改。首次资料练习不一定需要 worktree；第一次修改真实代码或并行工作时，隔离会更安全。

## 7.5 选择第一次权限模式

在输入区下方的权限控制中选择 **Ask for approval**。它允许 Codex 在当前工作区内完成常规任务，尝试越过边界时会暂停请求确认。

不要在第一次任务中启用 Full access。Full access 会移除文件系统与网络的重要限制，适合已经理解风险、且外部环境另有保护的特殊任务，不是减少弹窗的普通选项。

某些版本还可能显示 **Approve for me** 或自定义权限配置。自动审查不会扩大沙箱边界，但会改变由谁处理越界请求。入门阶段由自己看清每次请求，更容易理解工具和权限之间的关系。

权限模式是当前任务的边界，不是对结果正确性的保证。即使操作完全在项目内，也要检查它有没有改错文件或误解要求。

## 7.6 先运行只读环境检查

第一次不要马上要求修改。输入：

> 先只读检查当前项目，不要修改文件，不要联网。说明实际工作目录，列出能够看到的文件和文件夹，指出哪些是来源、哪些是输出位置。读取 README 中的任务说明，给出最小执行计划，并列出需要我确认的假设。

你要检查的不是回答是否漂亮，而是它有没有正确识别路径、文件与边界。若它看到不该出现的私人资料，立即停止并缩小项目范围；若缺少来源，先修正目录而不是让它猜。

Codex 可能运行列目录或读取文件的工具。查看活动记录，理解“只读”仍可能包含命令执行，但命令应该停留在允许范围内。

## 7.7 完成第一次写入任务

环境检查正确后，继续：

> 按计划读取 `sources` 中的全部会议记录，在 `output` 新建 `summary.md`。分为决定、待办、风险和未知项；每项注明来源文件。不要修改 `sources`，不要联网。完成后重新读取输出，检查是否遗漏来源，并报告创建了哪些文件。

任务完成后打开 `summary.md`，不要只看对话摘要。抽查几条结论是否能在来源中找到，检查原文件修改时间或 Git 状态，确认 `sources` 没有变化。

如果 Codex 请求网络或项目外写入，先问为什么。当前任务明确不需要这些权限，合理行为应该是留在工作区，而不是申请 Full access。

## 7.8 学会看三个结果位置

桌面 Codex 的结果通常分布在三个位置。

**对话记录**说明它做了什么、遇到什么问题和最终交付。它适合阅读总结，但不替代真实文件。

**文件与预览**展示成果本身。报告、表格、演示、图片或网页都应该打开检查；长文件要查看开头、中间和结尾，防止局部缺失。

**差异与终端**提供执行证据。Git 项目可以查看新增、删除和修改行；集成终端可以运行 `git status`、测试或项目检查。ChatGPT 能读取当前终端输出，帮助诊断失败。

“任务完成”应该能在这三个位置互相印证：对话说明成果，文件真实存在，差异或检查证明范围正确。

## 7.9 只配置必要设置

桌面应用设置可以通过应用菜单打开，macOS 常用 `Cmd+,`，Windows 常用 `Ctrl+,`。第一次只需要检查少数项目：

- **General**：长任务时是否阻止电脑休眠，以及跟进消息如何处理；
- **Notifications**：是否在任务完成时通知；
- **Permissions**：允许哪些权限模式出现在菜单；
- **Personalization**：表达风格和个人指令，不会提高模型能力；
- **Browser / Computer Use**：暂时不用就不必安装或授权；
- **Memories**：了解是否启用，不把它当作项目必需规则。

不要在上手当天同时配置 Chrome、Computer Use、MCP、插件、自动化和自定义代理。每增加一种能力，就增加一条数据与权限链路。等当前任务确实需要时，再单独安装和测试。

## 7.10 操作系统权限要按需授予

普通文件任务通常不需要屏幕录制或辅助功能权限。Computer Use、Chronicle 等能力在 macOS 可能请求 Screen Recording、Accessibility 或 Input Monitoring；Windows 的桌面控制也有自己的前台与沙箱要求。

只在理解功能和使用场景后授权。拒绝某项系统权限不会让基本 Codex 文件能力全部失效，只会限制依赖该权限的工具。以后不再使用时，可以回到系统隐私设置撤销。

如果系统弹窗与当前任务无关，先拒绝并查明来源。不要因为“让 AI 更强”而一次授予全部系统权限。

## 7.11 常见故障排查

**登录后没有 Codex。** 检查应用版本、账号方案、工作区和管理员授权。

**看不到文件。** 确认添加的是正确项目根目录，文件确实位于其中，并检查操作系统目录访问权限。

**能读不能写。** 查看当前权限模式、目标目录和文件自身权限；不要直接切到 Full access。

**任务一直请求网络。** 判断任务是否真的需要公网；本地命令、网页搜索、Browser 和插件有不同网络控制。

**终端命令失败。** 记录完整错误，确认依赖工具是否安装、项目环境是否正确。环境错误不应通过修改任务目标掩盖。

**结果似乎不在当前项目。** 查看任务的项目或 worktree 路径，再检查真实文件与 Git 状态。

报告问题时记录应用版本、操作系统、入口、当前项目和可复现步骤，不要公开日志中的敏感信息。

## 7.12 本章小结

桌面端上手的可靠顺序是：从官方来源安装，登录正确账号，选择 Codex，打开最小项目，使用 Ask for approval，先只读检查，再完成一次受限写入，最后查看文件、差异和验证结果。

> 第一次成功，不是 Codex 做得多，而是它只在你选定的项目里做了该做的事，而且你能证明这一点。

下一章将进一步解释项目、文件、对话、工作区和 worktree 应该怎样组织。
