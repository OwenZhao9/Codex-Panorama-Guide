# 第十三章：Work——从对话走向交付

周一上午，你要为下午的会议准备一份项目简报。材料散落在几份会议记录、一张进度表和一组用户反馈里，有些决定还留在协作平台中。你需要的不是一段泛泛的总结，而是一份可以直接打开、核对和修改的文件：先说明进展，再列出风险、负责人和下一步。

如果使用 Chat，你可以逐个提问，让 AI 帮你理解材料、讨论重点、修改几段文字。如果使用 Work，则可以直接描述最终成果，让智能体读取获准的资料、完成多个步骤、生成文件，并把结果交给你审阅。

两者都很有用。区别不在于谁“更聪明”，而在于你想进行一次对话，还是委托一项有明确结果的工作。

## 13.1 Work 是什么

OpenAI 将 Work 定义为一种把实际工作委托给 ChatGPT 的方式。它适合需要明确成果的任务，例如研究简报、分析报告、比较表格、演示文稿、项目计划、定期更新或可以继续使用的文件。

Work 不是一个独立模型，也不是“回答更长”的 Chat。它改变的是任务的组织方式：你先定义结果，智能体再根据需要使用文件、插件和获准的工具，连续完成收集、整理、分析、创建和检查等步骤。

在任务运行时，你仍然可以查看进度、补充信息、回答问题、改变方向，并在重要行动前作出确认。因此，Work 更接近“委托并验收”，而不是“提出问题并接收答案”。

还要注意，Work 与 Codex 的能力存在重叠。在桌面应用中，两者使用同一智能体核心：Work 更偏向日常知识工作和完成品，通常隐藏不必要的技术细节；Codex 更偏向软件项目，提供文件差异、Git、命令和代码审查等开发视图。如果你已经习惯在 Codex 中完成研究、文档或演示，也可以继续使用；选择 Work，主要是为了获得更适合日常工作的入口和呈现方式。

## 13.2 什么时候使用 Chat，什么时候使用 Work

可以用一个简单问题判断：**你现在需要的是回答，还是成果？**

| 任务特征 | 更适合 Chat | 更适合 Work |
| --- | --- | --- |
| 主要目的 | 理解、讨论、构思、短草稿 | 完成一项有明确结果的任务 |
| 任务长度 | 一两轮对话即可解决 | 包含多个来源、工具或步骤 |
| 典型输出 | 解释、建议、短文本 | 报告、表格、演示、项目计划或持续更新 |
| 使用方式 | 你主导每一轮对话 | 你定义结果、边界和验收标准 |

下面这些任务通常适合 Chat：

- 解释一个陌生概念；
- 帮你列出几个方向；
- 改写一段邮件；
- 比较两个简单选项；
- 在正式开始前澄清自己真正想要什么。

下面这些任务通常更适合 Work：

- 阅读多份材料并制作一份带来源的研究报告；
- 把会议记录转化为项目简报、待办和跟进草稿；
- 清洗一张表格并生成可编辑的比较结果；
- 根据调研材料制作一套演示文稿；
- 从固定来源定期生成状态更新；
- 使用多个插件或工具完成一条连续工作流。

这不是严格的功能边界。同一个任务可以先在 Chat 中讨论，再切换到 Work 完成交付；也可以先让 Work 生成初稿，再回到对话中逐步修改。真正重要的是任务当前处于哪个阶段。

## 13.3 什么样的任务最适合 Work

一个适合 Work 的任务通常具有四个特点。

第一，**有清晰结果**。你知道最后要得到报告、表格、演示、清单还是其他文件，而不只是“研究一下”。

第二，**需要实际材料**。任务依赖会议记录、数据文件、项目资料、网页或连接服务中的信息，而不是只靠通用知识就能完成。

第三，**包含多个步骤**。它可能需要先读取、再比较、然后创建，最后还要检查。手工完成会花费一段有意义的时间。

第四，**结果可以审阅或复用**。你能打开文件、核对数字、检查来源、提出修改，或者在以后继续更新这份成果。

相反，下面几类任务不应该直接丢给 Work：

- 目标还没有想清楚，也没有办法判断什么叫完成；
- 只是需要一句解释或一次快速判断；
- 缺少关键资料，却要求它作出确定结论；
- 希望它在无人确认的情况下发送、付款、公开发布或删除重要数据；
- 结果无法检查，失败后也难以恢复。

Work 可以帮助澄清目标，但不会替你决定什么真正重要；可以调用工具，但不会凭空获得权限；可以检查自己的成果，但不会因此变成绝对可靠。

## 13.4 Work 怎样完成一项任务

一项成熟的 Work 任务通常会经过五个环节。

### 一、理解结果

智能体先判断最终要交付什么、给谁使用，以及什么条件代表完成。如果目标仍然含糊，它可能先提问或提出计划。

### 二、建立上下文

它读取你上传的文件、项目资料和获准的连接来源，确认哪些材料可用、哪些内容缺失。正确的上下文往往比更长的提示词更重要。

### 三、执行多个步骤

它根据任务需要搜索、提取、计算、比较、整理或调用工具。你不必提前规定每一个动作，但应该说明不能越过的边界。

### 四、创建可审阅成果

Work 的目标不是只在聊天框里汇报“已经完成”，而是生成你能够查看、下载、修改或继续使用的结果。成果可以是文档、表格、演示、PDF，也可以是一套结构化分析。

### 五、检查并迭代

智能体按照验收标准进行检查，说明用了哪些来源、做了哪些核对、还有哪些内容不能确认。你审阅结果后，可以针对某一页、某张表或某一段提出修改，而不必从头开始。

这五个环节构成了一条完整链路：

> 结果 → 上下文 → 执行 → 交付 → 验收

如果一项任务只强调“执行”，却没有明确结果和验收，Work 也很容易在看似忙碌的过程中偏离目标。

## 13.5 给 Work 准备合适的上下文

Work 能使用什么，取决于你提供或授权了什么。常见上下文有四种。

| 上下文来源 | 适合的情况 | 需要注意 |
| --- | --- | --- |
| 当前聊天附件 | 只服务于这一次任务的文档、表格、PDF 或图片 | 确认文件版本和上传是否完整 |
| 项目文件与说明 | 多个任务长期使用同一批资料和规则 | 不同成果使用独立聊天，避免上下文混杂 |
| 插件与连接来源 | 信息位于网盘、邮件、日历或协作平台 | 访问仍受账号权限和组织策略限制 |
| 网页、本地文件和应用 | 任务需要当前网络信息或桌面环境 | 可用性取决于设备、界面、地区和设置 |

一次性的材料可以直接附加到当前聊天。持续数周的项目则更适合放进 Project，让相关聊天共享文件、来源和项目说明；每个独立成果仍应使用单独聊天，避免研究、写作和修改全部挤在一条漫长对话中。

插件适合读取外部系统中的资料或执行受控操作。例如，你可以让 Work 使用网盘中的项目计划和协作平台中的最新决定生成周报。但“安装了插件”不等于“获得所有数据”，它只能访问当前账号有权访问、且工作区策略允许的内容。

材料也不是越多越好。把整个网盘、几十个无关文件和模糊要求一起交给 Work，会增加误读旧版本和遗漏重点的可能。更好的做法是说明哪些来源最重要、时间范围是什么，以及发生冲突时以哪一份为准。

## 13.6 怎样写一个好的 Work 任务

你不需要学习复杂的提示词公式。对于重要任务，说明四件事通常就够了：

1. **结果**：要完成什么，给谁使用；
2. **材料**：使用哪些文件、项目或插件；
3. **边界**：什么不能改变，哪里必须停下来确认；
4. **验收**：什么条件代表成果可以交付。

例如，不要只说：

> 根据客户调研做一个演示。

可以改成：

> 使用项目中的访谈记录和调查表，为周五的产品评审制作一份不超过八页的演示。先给出三个最重要的发现，再说明证据、分歧和建议。所有数字都注明来源文件，受访者原话不要脱离上下文。不要发送或发布演示。完成后检查图表总数是否与原表一致，并列出无法确认的信息。

这段任务没有规定每一次搜索和每一个排版动作，却把结果、来源、边界和完成标准交代清楚了。它给智能体留下执行空间，也保留了人应该控制的部分。

## 13.7 在执行过程中怎样介入

委托 Work 不等于离开以后等待最终答案。你可以跟进进度、回答问题、增加材料或调整方向。关键是选择合适的介入时机。

出现下面情况时，应尽早纠正：

- 它误解了受众或成果形式；
- 使用了错误版本或遗漏关键来源；
- 对不确定信息作出未经说明的假设；
- 准备执行超出原定范围的操作；
- 阶段成果已经显示方向有误。

如果方向正确，则不必为每一个微小步骤作决定。频繁改变目标会让任务失去稳定中心。更好的做法是在关键节点检查：材料是否齐全、结构是否合理、重要数字是否可信、最终文件是否可以使用。

涉及对外发送、公开发布、权限变更、购买或删除数据时，应明确要求“先准备，行动前等待确认”。即使界面会显示权限请求，也不要只依赖系统提醒来表达你的真实边界。

## 13.8 怎样验收 Work 的成果

Work 的完成提示不是验收证据。真正的验收要回到成果本身。

| 成果类型 | 至少检查什么 |
| --- | --- |
| 报告与简报 | 关键结论、来源、日期、遗漏和未经支持的推断 |
| 表格 | 行数、字段、公式、总计、异常值和原始数据是否被改动 |
| 演示文稿 | 每一页的逻辑、文字溢出、图表标注和数字一致性 |
| 定期更新 | 数据时间范围、来源是否更新、失败时是否明确报警 |

可以继续追问：

- 你实际使用了哪些来源？
- 哪些文件或页面无法访问？
- 哪些结论包含假设？
- 你做了哪些检查，证据在哪里？
- 如果补充一项信息，什么最可能改变结论？

打开并检查每一页、每个工作表或每一张幻灯片。重要数字、姓名、日期、引文和外部事实应回到原始来源核对。法律、医疗、财务、安全等高风险成果还需要相应专业人员审阅。

## 13.9 五个常见误区

**误区一：Work 会让答案自动正确。** Work 增加的是执行和交付能力，不会消除模型错误、过期资料或错误假设。

**误区二：给的材料越多越好。** 无关信息会稀释重点，旧版本还可能造成冲突。上下文应当相关、明确并有优先级。

**误区三：所有问题都应该使用 Work。** 快速解释、讨论和短改写使用 Chat 更省时间，也通常消耗更少。

**误区四：第一版文件就是成品。** 第一版的价值是让你看到结构和问题，后续应使用批注或具体反馈做定向修改。

**误区五：连接工具等于完全授权。** 插件、浏览器和本地文件仍受账号、权限、沙箱、工作区策略及人工确认约束。

## 13.10 第一次实践：制作一份比较简报

准备两到三份你熟悉的材料副本，例如三个产品介绍、几份活动方案或两个月的项目记录。选择 Work，然后输入：

> 阅读我提供的全部材料，制作一份一页比较简报和一张比较表，供我自己做决定。先说明比较对象和评价维度，再列出共同点、主要差异、风险和仍然缺失的信息。只使用这些材料，不要用常识补齐空白；每个关键结论注明来源文件。不要修改原文件，也不要对外发送。完成后检查是否遗漏材料，并说明你做过哪些核对。

预期得到三部分成果：

1. 一页能够快速阅读的结论摘要；
2. 一张维度一致、可以继续编辑的比较表；
3. 一份来源、缺失信息和检查结果清单。

验收时确认：所有输入文件都被正确识别；比较维度前后一致；结论能够追溯到材料；不确定信息没有被伪装成事实；原始文件没有被修改。

这个练习的重点不是比较本身，而是体验完整的 Work 循环：你定义成果，提供上下文，设置边界，智能体执行并交付，最后由你验收。

## 13.11 本章小结

Work 是把有明确结果的实际任务委托给 ChatGPT 的工作方式。它适合多来源、多步骤、需要文件或持续更新，并且最终成果可以审阅和复用的任务。

使用 Work 时，最重要的不是写出华丽的提示词，而是说明结果、材料、边界和验收标准；执行过程中在关键节点介入，完成后回到原始来源和实际文件进行检查。

记住这句话：

> Chat 帮你把事情想明白，Work 帮你把成果做出来。

当任务复杂到需要先澄清问题、比较路线和安排步骤时，不要急着执行。下一章将介绍计划模式（Plan Mode），以及怎样在真正行动前把复杂任务想清楚。
