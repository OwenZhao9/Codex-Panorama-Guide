# 第三十八章：实战案例五——创建网站与在线工具

一个在线工具是否有价值，不取决于页面用了多少动画，而取决于用户能否顺利完成一件事。本章以“活动预算计算器”为例：用户输入参与人数、场地、材料、餐饮和人员成本，工具计算总预算、人均成本，并生成一份可复制的费用摘要。

这个案例展示从需求、数据规则、界面原型到浏览器验收和发布的完整过程。你不需要编程基础，也不必真的上线这个工具。重点是学会把一个模糊想法变成可以测试的行为，并知道保存版本、部署生产和分享链接之间的区别。

## 38.1 把想法改写成用户任务

“做一个活动预算网站”仍然太宽。先写一张产品卡：

- 目标用户：需要快速估算小型活动费用的组织者；
- 核心任务：五分钟内得到总预算和人均预算；
- 主要输入：人数、场地、材料、餐饮、工作人员、预备金比例；
- 主要输出：分类小计、总额、人均成本和可复制摘要；
- 成功标准：首次使用者无需说明也能完成计算；
- 首版不做：账号、在线支付、供应商报价和团队协作。

接着写出三个真实场景：一场 20 人的读书会、一场 80 人的工作坊和一场没有餐饮的小型会议。每个场景都包含输入和预期结果，它们既是设计材料，也是后面的验收测试。

首版有意保持无登录、无持久化数据。主题颜色、折叠状态等临时界面偏好可以留在浏览器中；用户只需要一次估算，不必为了“看起来像产品”就建立数据库。只有当用户明确需要保存多个方案、跨设备继续或与他人共享时，才考虑持久化和身份系统。

## 38.2 先定义计算规则

界面之前，先写规则表。每个字段说明单位、默认值、范围和计算方式：

| 字段 | 示例规则 |
| --- | --- |
| 参与人数 | 必须是 1—10,000 的整数 |
| 场地费 | 非负金额，可按场次输入 |
| 材料单价 | 非负金额，乘以参与人数 |
| 餐饮单价 | 可为零，乘以参与人数 |
| 工作人员 | 人数 × 小时 × 时薪 |
| 预备金 | 直接成本小计 × 0%—30% |
| 人均成本 | 总预算 ÷ 参与人数 |

还要定义币种和舍入规则。金额输入为空时是“尚未填写”还是零，应保持一致；人数为零时不能进行除法，而应提示用户输入有效人数；负数、文字和超大数值需要明确反馈。生成的摘要应复用同一计算结果，不能另写一套公式。

把规则文件作为唯一计算依据。如果以后修改预备金范围或增加税费，先更新规则和测试场景，再改变界面。

## 38.3 画出最小页面结构

首版只需要一页：

1. 标题和一句用途说明；
2. 费用输入区，按固定、按人和人员费用分组；
3. 结果摘要区，突出总预算与人均成本；
4. 分类明细和预备金说明；
5. 复制摘要、重置和示例数据操作；
6. 简短的隐私与计算说明。

桌面端可以左右分栏，移动端应按输入、结果、明细的顺序垂直排列。不要把重要结果只用颜色区分；输入必须有可见标签，错误提示与字段相邻，键盘可以到达所有控件，焦点状态清晰。

先让 Codex 生成文字线框和交互说明，再创建 Site。这样可以在低成本阶段发现缺失字段和顺序问题，不必每次在成品页面上返工。

## 38.4 让 Sites 创建可审查版本

在支持的账户中，可以从 Sites 开始，或在提示里明确提到 `@Sites` 和“website”。Sites 当前处于公开测试，能否使用取决于套餐、地区和工作区设置。若不可用，同一份产品卡和规则仍可用于本地网站项目或其他建站工具。

第一次请求应包含受众、核心任务、计算规则、页面结构、视觉方向和验收要求。例如要求简洁、中性、移动优先，不使用登录和外部追踪，不把输入发送到服务器。

先要求保存版本，不部署。Sites 的发布分两步：保存版本形成可审查候选；部署版本才会生成生产 URL。每一个部署 URL 都是生产部署，因此不要把“部署看看”当成无影响预览。即使访问范围受限，发布也仍然是一个外部状态变化，需要明确确认。

## 38.5 用批注做小范围修改

初版出来后，不要重新描述整个网站。先按任务走一遍，再用批注或具体区域反馈：

- “把人数错误提示放到输入框下方，其他布局不变”；
- “移动端先显示总额，再显示费用明细”；
- “复制按钮成功后显示文字反馈，不要只改变颜色”；
- “保留所有计算规则，只降低标题区高度”。

小范围指令能减少无关漂移。若修改计算规则，要同时更新规则表和验收样例。若视觉调整导致输入顺序或标签改变，也要重新进行键盘和屏幕阅读检查。

版本命名应表达状态，例如 `v0.1-logic`、`v0.2-mobile`、`v0.3-accessibility` 和 `v1.0-candidate`。保留每版的主要变化、未解决问题和对应测试结果，方便回退。

## 38.6 在真实浏览器中验证行为

网站不能只靠截图验收。使用内置 Browser 或合适的浏览器工具，按测试场景实际输入和点击。至少覆盖：

- 默认页面：未输入时不显示误导性的有效结果；
- 正常小型活动：计算与手工结果一致；
- 大型活动：金额格式和布局不会溢出；
- 无餐饮场景：零值正确，不出现无意义错误；
- 非法人数：零、负数、小数、文字和空值；
- 边界预备金：0% 与最大允许值；
- 复制摘要：文字与页面结果一致；
- 重置：所有字段、错误和结果回到初始状态；
- 移动宽度：无横向滚动，按钮可点击；
- 键盘路径：顺序合理，焦点清晰，不会困住用户。

对三个示例场景手工计算预期总额和人均值，再与页面比较。只验证页面“有数字”是不够的。若使用自动化测试，也要进行一次人工视觉巡检，因为自动检查不一定能发现重叠、字体过小或错误信息难以理解。

如果工具连接了存储、登录或上传，测试范围要进一步扩展：数据是否真的跨访问保留；不同用户是否互相隔离；退出登录后是否仍能看到私有内容；删除行为是否符合说明。身份只是知道用户是谁，授权仍要在服务端判断用户可以访问什么。

## 38.7 发布前决定访问和数据策略

这个首版不保存数据，隐私说明可以明确表示计算在当前会话中完成，并提醒用户不要输入敏感信息。如果以后增加保存功能，应回答：保存什么、保存多久、谁能访问、怎样删除、是否需要登录、是否包含个人或商业敏感数据。

发布前确认：

- 最终候选版本和测试记录；
- 公开、仅工作区或其他访问范围；
- 页面标题、描述、图标和分享预览；
- 联系方式、隐私说明和使用边界；
- 生产链接由谁保管和分发；
- 出现错误时怎样回退或停止分享；
- 上线后多久查看分析和用户反馈。

Sites 可以记录访问分析，但数据不等于答案。页面浏览多并不能证明计算器有帮助；更有意义的信号可能是完成计算、复制摘要、重复使用和用户报告的节省时间。任何额外追踪都应有明确目的。

## 38.8 可直接复制的任务提示

```text
请创建一个移动优先的活动预算计算器网站。

目标用户是在五分钟内估算小型活动总预算和人均成本的组织者。输入包括参与人数、场地费、材料单价、餐饮单价、工作人员人数/小时/时薪和预备金比例。输出包括分类小计、总预算、人均成本和可复制摘要。

先建立产品卡、计算规则表、文字线框和验收场景，再创建网站。首版不使用登录、数据库、上传、外部分析或支付；不要把用户输入发送到服务器。金额不得为负，人数必须是正整数，预备金为 0%—30%。定义币种、空值和舍入规则。

页面必须支持移动端、键盘操作、可见标签、就地错误提示、明显焦点和不依赖颜色的状态反馈。提供示例数据、复制摘要和完整重置。

创建后只保存可审查版本，不要部署。使用三个给定活动场景和边界输入验证计算、复制、重置、移动布局和键盘路径；手工复算关键结果。最后报告版本、测试证据、已知限制和发布前仍需确认的事项。
```

## 38.9 失败时怎样诊断

如果计算错误，先检查规则和中间值，不要先改界面。如果同一输入偶尔得到不同结果，确认是否存在重复事件处理、隐藏默认值或不同公式。如果手机页面难用，减少同时显示的信息，让结果和主要操作按任务顺序出现。

如果 Site 变得越来越复杂，回到首版“不做”清单。保存账户、供应商报价和团队共享都是新的产品阶段，不应顺手加入。如果部署后才发现问题，停止继续分享，修复并验证新版本，再有意识地部署；不要让多个生产链接在没有说明的情况下并存。

## 38.10 本案例的能力边界

Codex 和 Sites 能缩短原型、修改和部署流程，但不会自动保证计算正确、页面无障碍或数据处理合规。涉及财务报价、税费、医疗、法律或其他高风险计算时，需要领域专家和更严格测试。Sites 的可用性、限制和界面会变化，应以账户当前显示和官方文档为准。

这个案例可以复用的核心是：产品卡、规则表、验收场景、版本记录、浏览器测试和发布确认。它们让“做一个网站”变成一个可以证明是否完成的产品任务。
