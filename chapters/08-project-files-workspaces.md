# 第八章：项目、文件与工作空间

Codex 回答“找不到文件”，未必是模型能力问题；它改了错误版本，也未必是推理不足。很多失败来自项目边界不清：资料散落在不同位置、同名版本并存、任务打开了错误目录，或者临时对话被当作长期项目。

组织工作环境的目的不是让文件夹看起来整齐，而是让 Codex 能确定：哪些材料属于当前任务，哪些规则应该持续，哪里可以写入，怎样检查变化。

## 8.1 项目、对话和文件夹不是一回事

**项目**组织一组长期相关的对话、文件、指令和来源。例如“年度行业研究”可以包含资料收集、数据清理、报告写作和演示制作等多个任务。

**对话或任务**应该围绕一个明确结果。即使它属于长期项目，也不应把所有工作塞进同一条对话。分别建立“核验数据”“写第一版报告”“审查引用”等任务，能减少上下文污染。

**本地文件夹**是 Codex 实际读取和修改文件的范围。一个本地项目可以连接一个或多个文件夹，但应尽量只包含相关内容。文件夹决定工作对象，项目负责组织上下文，对话负责一次具体成果。

**ChatGPT Project**则可以在相关对话间共享上传文件、项目指令和连接来源。它与本机文件夹项目有联系，但不是同一概念。网页项目不会自动变成本地目录，本地目录也不会自动上传到网页。

## 8.2 什么时候应该创建项目

满足任一条件时，适合建立项目：

- 工作会持续多次，不是一问一答；
- 多个成果依赖同一批材料；
- 有长期术语、格式或检查规则；
- 需要在不同任务间共享来源；
- 希望统一归档、搜索和继续工作。

一次短改写、一个独立问题或不需要共享文件的任务，可以直接开始对话。不要为每个小问题创建项目，也不要用一个“所有工作”项目容纳完全无关的内容。

项目名应描述真实范围，例如“2026 夏季新品发布”，而不是“工作”“临时”或“Codex”。对话标题则描述具体结果，例如“竞品价格核验”或“发布演示第一版”。名称本身就是减少误操作的第一层上下文。

## 8.3 怎样选择项目根目录

项目根目录应该包含完成任务所需文件、规则和验证方式，同时排除无关私人资料。选择时问：如果 Codex 能看到这个目录下全部内容，是否合理？如果它只能写入这个范围，能否完成任务？

范围过大会暴露不必要信息，并让搜索结果混乱；范围过小则会缺少共享模板、依赖或测试。对于包含多个独立应用的大型仓库，可以分别添加更小的本地项目；需要跨目录工作时，再明确增加必要根目录，而不是打开整个磁盘。

Git 项目通常以包含 `.git` 的目录作为项目根。Codex 会从当前目录向上寻找项目配置与 `AGENTS.md`，因此在错误子目录启动，可能加载不同规则或遗漏必要文件。

打开项目后，让 Codex 先报告当前工作目录、项目根和主要文件，比直接开始修改更安全。

## 8.4 建立清楚的文件结构

没有唯一正确的结构，但应该区分来源、工作过程和交付物。例如：

```text
research-project/
├── AGENTS.md
├── README.md
├── sources/
│   ├── interviews/
│   └── reports/
├── data/
│   ├── raw/
│   └── processed/
├── drafts/
├── deliverables/
└── checks/
```

`sources` 和 `data/raw` 尽量保存原始材料，修改后的内容进入 `processed`、`drafts` 或 `deliverables`。这样既能追溯来源，也能防止清理过程覆盖原件。

README 可以说明项目目标、目录含义、当前版本和验收方式。文件名使用稳定格式，包含主题与日期；不要依赖“最新”“最终2”“真的最终”区分版本。时间敏感资料应记录数据截止日，而不仅是文件修改日期。

## 8.5 上传文件与本地文件怎样选择

只与一次网页任务有关的少量材料，可以直接附加到对话。需要在同一项目多个对话中使用的文件，可放进 ChatGPT Project 的 Sources。需要频繁更新、大批量处理或由本地工具修改的内容，更适合本地项目。

上传是创建一个任务可访问的副本，不要假设它会与电脑原文件自动同步。你后来修改本地文件，旧对话中的上传版本仍可能是旧的。提示中应写明版本日期，并在重要任务开始前确认实际来源。

同样，本地项目不会自动看到网盘、邮件或项目管理工具。需要这些数据时，应导出文件，或通过经过授权的插件、连接器和 MCP 访问。

附件只影响当前任务时，不必放进长期项目；长期来源也不要每次重复附加不同副本。来源范围越清楚，越容易追踪结论。

## 8.6 Codex 能处理哪些文件

Codex 可以处理常见文本、代码、Markdown、数据、文档、表格、演示、PDF 和图片等文件，但“能够读取”不等于所有内容都能完整理解。

扫描 PDF 可能需要文字识别；复杂表格可能包含隐藏工作表、外部链接和宏；演示有视觉布局问题；图片中的小字可能无法准确识别；专有格式可能缺少解析工具。任务开始时应先做文件清单与可读性检查。

处理批量文件时记录成功、失败和跳过数量。不能读取的文件要单列，不应在总结中悄悄消失。对原生格式生成成果后，还应打开预览，验证页面、工作表、公式和布局。

## 8.7 用 `AGENTS.md` 保存项目指导

项目中长期有效的要求可以写进 `AGENTS.md`。它像给智能体看的项目说明，会随项目上下文自动加载。

适合写入的内容包括：

- 项目目标和目录说明；
- 哪些文件是原件，禁止直接修改；
- 常用运行、检查和测试命令；
- 输出格式、术语与语言要求；
- 提交、审查和发布流程；
- 需要人工确认的高风险操作。

规则要短、具体、真实可执行。“保证高质量”没有帮助；“修改 Markdown 后运行链接检查，并报告失败 URL”才是有效指导。

可以在不同目录放置更具体的 `AGENTS.md`，靠近当前文件的规则优先。不要把 Secret 写进指导文件，也不要用它替代真正沙箱。`AGENTS.md` 影响行为，权限系统才执行技术边界。

## 8.8 `.codex` 目录负责什么

可信项目可以在 `.codex/` 中保存项目级配置、环境设置、规则或其他 Codex 资源。例如本地环境会把设置脚本和常用 Actions 放在项目根的 `.codex` 下，团队可以把它们加入 Git 共享。

项目配置不是普通内容文件。它可能影响模型、工具、网络、Hooks 和命令行为，只有在你信任项目时才应加载。官方实现会忽略不受信任项目的项目级 `.codex` 层，这是重要安全边界。

不要从陌生仓库复制整套 `.codex` 配置后直接信任。先阅读其中命令、脚本、MCP 地址和 Hooks，确认不会上传数据、安装未知软件或扩大权限。

入门项目不必立刻创建复杂 `.codex`。当安装依赖、启动服务或检查命令反复出现时，再把稳定步骤配置为环境和 Action。

## 8.9 Git、分支和 worktree

Git 记录文件变化，适合需要持续修改的项目。开始任务前查看工作区是否已经有未提交内容；这些可能属于你或其他工具，Codex 不应随意覆盖。

分支把一组变化与稳定主线分开。worktree 则为分支或任务提供独立工作目录，适合并行任务和后台写入。在桌面 Codex 中，新对话可以从当前项目或隔离 worktree 开始。

worktree 能防止两个任务直接改同一份工作区文件，却不能解决逻辑冲突。合并前仍需查看差异、运行检查，并确认两个方案兼容。

非 Git 项目没有自动版本历史。重要原始文件应保留副本，批量操作先在样例上测试。不要因为 Codex 可以“撤销一步”，就把它当作可靠备份系统。

## 8.10 忽略文件不等于保护隐私

`.gitignore` 只告诉 Git 默认不要跟踪某些文件，并不会阻止 Codex 或本地命令读取它们。项目中的 `.env`、凭证、客户导出和个人数据仍可能进入任务上下文。

敏感文件应从不需要它们的工作区移除，或通过文件权限与 Codex permission profile 明确设为 deny。使用样例配置替代真实 Secret，例如提供 `.env.example`，只保留变量名和非敏感示例。

生成成果也要检查隐私。摘要可能暴露原文中的私人姓名，截图可能包含通知，日志可能打印 token。提交或分享前，对新增文件与差异做一次敏感信息审查。

## 8.11 项目中的多任务怎样组织

同一项目内，为不同结果建立独立对话。例如研究项目可以有“来源清单”“数据清理”“报告初稿”“事实核验”和“演示制作”。这样每个任务的上下文更聚焦，项目仍共享长期材料与规则。

相关工作需要延续时继续原对话；目标已经改变或需要独立并行时新建对话。Pin 只改变显示位置，不会增加上下文；Archive 用于整理完成任务，也不应被当作删除数据。

对话之间交接应使用明确成果，例如文件路径、提交、来源清单和决定记录，而不是假设另一个任务自动知道前一条对话所有细节。

## 8.12 第一次实践：建立可审计项目

把练习目录初始化为清楚结构，然后提出：

> 先只读检查当前项目。说明项目根目录、文件结构、版本状态和已有规则。识别原始来源、可写输出和可能包含敏感信息的文件；不要打开或输出疑似 Secret 的内容。提出一个最小重组方案，让原始材料保持不变、成果集中到 `deliverables`，并给出重组后的验收清单。等我确认后再修改。

确认后让 Codex 只移动练习副本或创建新目录，再查看完整差异。验收包括：原始文件数量不变；输出位置明确；README 说明结构；没有把敏感文件纳入版本控制；所有移动都可以恢复。

## 8.13 常见误区

**项目就是一个长对话。** 项目共享长期上下文，对话应围绕单一结果。

**打开更大目录能让 Codex 更懂我。** 无关内容会增加隐私风险和上下文噪声。

**上传文件会与本地自动同步。** 上传内容通常是任务可访问的版本副本。

**`.gitignore` 能阻止 Codex 读取。** 它只影响 Git 默认跟踪行为。

**worktree 会自动合并所有成果。** 它隔离目录，最终仍需审查与合并。

## 8.14 本章小结

项目组织长期上下文，对话承载具体成果，工作目录决定本地文件范围。用清楚结构分离来源、过程和交付物，用 `AGENTS.md` 保存长期规则，用 Git 与 worktree 记录和隔离变化，并用权限保护敏感路径。

> 好的工作空间让 Codex 不必猜“该看什么、该改哪里、怎样算完成”。
