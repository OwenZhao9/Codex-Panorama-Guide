# 第二章：Codex 基础认知

第一次打开 Codex，很多人会把注意力放在模型选择器、输入框和各种按钮上，却忽略了最重要的问题：它正在什么环境里工作？能看到哪些材料？可以使用哪些工具？最后应该交付什么？

Codex 的使用难点通常不在“会不会写提示词”，而在能否建立正确的任务模型。只要理解一项任务由什么组成，即使界面以后变化，也能判断该把材料放在哪里、该开放哪些权限、该怎样检查结果。

## 2.1 Codex 究竟是什么

Codex 是 OpenAI 面向软件开发和项目执行的 AI 智能体。它能够理解项目、读取与修改文件、运行命令、使用工具、检查差异，并围绕一个结果连续工作。

“面向软件开发”不等于“只能编程”。代码项目只是文件、规则、工具和验证都比较清楚的一类工作环境。同一套智能体能力也可以用于研究、数据、文档、演示、网站和日常项目。当前 ChatGPT 的 Work 模式与 Codex 使用相同的核心智能体能力，但界面表达不同：Work 偏向普通工作成果，Codex 会显示更多项目、终端、Git 和技术细节。

因此，可以同时保留两个准确理解：

- 严格说，Codex 是以软件和项目执行为核心的智能体产品；
- 从使用方法看，Codex 所代表的智能体工作方式远远超出写代码。

本书会在需要精确区分时使用 Chat、Work、Codex 和 Sites 的正式名称；讨论共同方法时，则把它们放进“Codex 工作生态”中理解。

## 2.2 一项任务的八个基本部分

可以用下面八个部分理解任何 Codex 任务：

| 部分 | 它回答的问题 |
| --- | --- |
| 目标 | 最后要得到什么结果？ |
| 上下文 | Codex 需要知道什么背景？ |
| 材料 | 要读取哪些文件、网页或外部数据？ |
| 环境 | 工作发生在网页、云端还是本地项目？ |
| 工具 | 它可以调用哪些程序、浏览器或连接服务？ |
| 权限 | 哪些内容可读、可写、可联网或可对外操作？ |
| 过程 | 是否需要计划、检查点、并行或持续运行？ |
| 验收 | 什么证据证明结果已经完成？ |

模型只是其中一项底层选择。模型很强，但材料给错、目录打开错、权限不足或目标含糊，结果仍然会失败。相反，任务结构清楚时，默认模型往往已经可以完成大量工作。

遇到问题时，也可以按这八层排查。它说没找到文件，先看材料和环境；不能搜索网页，检查工具与网络权限；结果方向不对，回到目标和上下文；任务显示完成却不可用，说明验收写得不够具体。

## 2.3 任务、对话、项目和工作区

这些词看起来相近，却表示不同范围。

**任务或对话**是一次持续协作的记录。你的要求、补充材料、Codex 的行动和结果都积累在其中。相关工作继续在同一任务中，可以保留上下文；互不相关的工作则应分开，避免旧信息干扰。

**项目**把一组相关任务、文件和规则组织在一起。例如“出版一本书”可以是项目，目录设计、章节写作和链接检查分别是不同任务。项目提供长期范围，但每个任务仍应有明确结果。

**工作区或工作目录**是 Codex 实际能读取和修改的文件范围。本地任务打开哪个文件夹非常重要：打开父目录可能暴露无关内容，打开过深的子目录又可能缺少必要文件。云端任务则使用检出的仓库和配置环境，不会自动看到你的桌面。

**工作树（worktree）**是 Git 项目的一种隔离工作目录。它让一个任务在不直接碰当前修改的情况下工作，适合并行或后台变更。它不是项目的同义词，也不会自动解决两个方案之间的逻辑冲突。

## 2.4 上下文不是越多越好

上下文包括当前提示、对话历史、项目文件、规则、记忆、工具返回和外部资料。Codex 根据这些信息理解“现在应该做什么”。

信息不足会让它猜测，信息过多也会产生问题。把整个网盘、所有历史对话和几十份无关文档交给任务，真正关键的约束可能被淹没。长任务还会累积搜索日志、错误输出和已经失效的中间结论，形成上下文污染。

合适做法是提供“会改变结果的信息”：目标受众、指定来源、当前版本、不能改变的内容、输出格式和验收标准。探索产生的大量噪声可以放进独立任务或子智能体，主任务保留决策和最终证据。

还要区分临时要求和持久规则。只对当前任务有效的边界写在提示中；项目长期遵守的命令、规范和检查方式可写进 `AGENTS.md`；重复工作方法可以整理成 Skill。不要期待一段旧对话永远代替正式规则。

## 2.5 工具让能力进入真实环境

Codex 本身负责理解和决策，工具负责接触真实对象。常见工具包括：

- 文件系统，用于读取、创建和修改文件；
- 终端，用于运行脚本、测试、转换和 Git 命令；
- 网络搜索，用于查找公开资料和当前信息；
- Browser，用于在隔离网页环境中浏览和操作；
- Chrome 扩展，用于在你的个人浏览器会话中工作；
- Computer Use，用于操作没有专用接口的桌面界面；
- 插件、连接器和 MCP，用于访问外部服务与数据；
- Skill，用于调用一套可复用的工作方法。

工具可用不等于每次都应使用。能用结构化文件就不必模拟点击；能通过官方连接器读取数据，就不应抓取不完整页面；只需分析时，不要开放写入。

Codex 也必须相信工具返回的真实状态，而不是自己的预期。命令失败、网页打不开、文件不存在时，它应该调整或报告，不能用“理论上应该成功”代替结果。

## 2.6 权限是任务设计的一部分

权限不是最后弹出的一道麻烦提示，而是任务定义的一部分。它决定 Codex 可以读取哪些路径、能否修改文件、是否能联网，以及是否可以使用外部应用。

最实用原则是：从完成任务所需的最小权限开始。

只做研究时先只读；需要生成成果时只写入指定目录；只访问两个来源时不开放任意网络；需要起草邮件时先禁止发送。任务稳定且风险可控后，再逐步扩大权限。

沙箱把程序限制在允许范围内，审批则在特定行动前要求确认。二者都不是正确性保证：一个操作即使符合权限，也可能不符合你的真实意图。权限控制“能不能做”，验收控制“做得对不对”。

## 2.7 本地运行与云端运行

本地任务靠近你的文件、软件和当前工作环境。它适合处理本机项目、使用已安装工具、查看本地预览和进行交互式修改。代价是需要更谨慎地保护个人文件和未提交变化。

云端任务在隔离容器中检出指定仓库版本，按照设置脚本准备环境，再执行工作。它适合后台运行、独立变更和可复现配置，但不会自动获得本地未提交文件、个人软件或未连接资料。

选择时问：真实材料在哪里？任务是否必须在我电脑上运行？是否需要隔离当前修改？完成后怎样把结果带回主项目？这比笼统问“云端和本地哪个更强”更有意义。

## 2.8 交付物比回答更重要

Codex 任务的结束不应只有一句“已经完成”。真正交付可能是：

- 一份带来源的报告；
- 可以打开并检查的表格或演示文稿；
- 一组修改后的文件和清晰差异；
- 可访问的网站版本；
- 测试、预览或核验结果；
- 一份说明未知项、失败步骤和后续决定的总结。

一个结果是否“可审阅”，取决于你能否打开、追溯和复现。报告要能找到来源；表格要检查公式；网站要实际访问；代码要查看 diff 和测试。Codex 自己说“检查过”只是线索，证据才是验收依据。

## 2.9 一次可靠任务的基本循环

不论界面如何变化，都可以使用同一条基本路径：

1. **定义**：说明成果、材料、边界和完成标准；
2. **理解**：让 Codex 确认实际环境、文件和未知项；
3. **计划**：复杂任务先拆步骤和检查点；
4. **执行**：在获准范围内使用工具推进；
5. **验证**：运行检查、查看来源、差异或预览；
6. **交付**：给出成果、证据、限制和下一步。

简单任务不必把六步写成仪式，但重要任务不能跳过理解和验证。执行得越快，越要防止在错误方向上快速前进。

## 2.10 第一次实践：先做环境体检

在一个只包含资料副本的练习文件夹中开始任务：

> 先不要修改任何文件。说明当前工作目录是什么，列出能够看到的文件和类型，判断哪些与“制作一份材料摘要”相关。指出无法读取、重复或可能过期的内容，并提出一个最小执行计划。计划必须包含最终成果、不会触碰的内容和验收方法；等我确认后再执行。

检查 Codex 是否真的列出了当前文件，而不是泛泛描述；是否区分事实与猜测；是否理解只读边界；计划中有没有可观察的完成标准。

完成这次体检以后，你会发现：正确环境和上下文往往比一句漂亮提示更重要。

## 2.11 常见误区

**Codex 就是一个模型。** 模型只是底层能力，实际任务还受上下文、工具、权限和环境影响。

**项目越大，开一个长对话越方便。** 无关工作混在一起会污染上下文；应按相关性组织任务。

**权限越高，完成率越高。** 过度权限扩大风险，并不能修复错误目标。

**云端能看到本机的一切。** 云端只看到被检出、上传或连接的内容。

**生成了文件就算完成。** 文件还需要打开、检查和对照原始要求。

## 2.12 本章小结

Codex 是能够在具体环境中读取材料、调用工具、执行步骤并交付结果的智能体。理解它，不能只看模型，而要同时看目标、上下文、材料、环境、工具、权限、过程和验收。

> 一项 Codex 任务是否可靠，取决于它能否在正确环境里，以合适权限处理正确材料，并用证据证明结果。
