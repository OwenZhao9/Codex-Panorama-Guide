# 第二十九章：代码、Git 与项目管理——让修改可追踪、可验证

你不一定是程序员，也可能需要维护一个个人网站、自动化脚本、数据看板或团队知识库。真正让人紧张的往往不是“代码”两个字，而是：改错了怎么办？怎样知道改了什么？能不能回到原来的版本？别人如何接着做？

Codex 可以阅读项目、修改文件、运行检查、解释差异并协助提交，但可靠交付仍要依靠清楚的任务、可验证的修改和版本记录。Git 为变化留下历史，测试帮助判断结果，项目管理则让多人知道为什么要改、改到什么程度。

> Codex 可以加快修改，Git 和验收让修改可追踪、可讨论、可恢复。

## 29.1 把编程放回全景能力中

代码不是 Codex 的全部，却是它最成熟的应用之一。前面讲过的计划、目标、文件、研究、Skill、MCP、自动化和并行任务，在软件项目里同样适用。

编程任务也不只是“生成一段代码”。一项完整工作通常包括：理解现状、确认需求、定位相关文件、提出最小改动、运行验证、审查差异、记录原因，再决定是否发布。Codex 的优势是可以参与这条完整链路，而不是只给出一段需要你自行粘贴的答案。

不会编程也可以使用这些能力，但需要把验收标准写成你能理解的结果。例如不要只说“优化前端组件”，而要说“手机上标题不换行遮挡，按钮能点击，原有桌面布局不变，并提供预览或截图”。越接近可观察结果，越容易验证。

## 29.2 修改之前先理解项目

成熟项目有自己的结构、术语和约束。直接要求“帮我加一个登录功能”，可能遗漏现有账号系统、隐私规则、部署方式和测试要求。

开始时先让 Codex 回答：这个项目做什么；入口在哪里；相关文件有哪些；目前怎样运行和测试；是否存在项目规则；工作区有没有未提交修改。对较大的任务，再要求它说明准备修改的范围和不打算动的部分。

一个稳妥的首次提示可以是：

> 先只读检查这个项目，不要修改文件。解释目录结构、启动方式、与“联系我们”页面相关的文件、现有测试，以及项目规则。列出当前未提交修改，并指出哪些可能与本任务冲突。最后给出最小修改方案和验收方法。

这一步不是形式主义。它能发现任务是否打开了错误目录、依赖是否缺失、当前分支是否正确，以及用户已有修改是否需要保护。任何现有未提交内容都应视为用户资产，不能随意覆盖或回退。

## 29.3 用 `AGENTS.md` 保存项目规则

反复出现在提示里的约定，适合写进 `AGENTS.md`。它可以描述项目结构、常用命令、命名规范、禁止修改的区域、测试方式和交付要求。Codex 会在项目上下文中读取相应规则；更靠近当前目录的文件可以提供更具体的要求。

好的规则短而具体，例如：

- 修改正文后运行链接检查；
- 不直接编辑自动生成目录；
- 用户可见文本使用简体中文；
- 提交前运行 `npm test` 和 `npm run lint`；
- 不把密钥、真实客户数据或本地配置加入 Git。

“写出高质量代码”过于抽象，不能指导实际选择。规则应来自反复发生的摩擦，并随着项目变化更新。过时的命令比没有命令更危险；如果主文件太长，可以引用专门的测试或审查说明。

## 29.4 把任务写成一个可验收的变更

代码提示至少包含四部分：

1. **目标**：用户最终能看到什么变化；
2. **背景**：问题在哪些页面、数据或流程中出现；
3. **约束**：哪些行为、接口、文件或风格不能改变；
4. **完成条件**：要运行哪些检查，怎样展示结果。

例如：

> 修复手机屏幕下报名表横向溢出的问题。保持字段、校验和桌面布局不变，不引入新依赖。先复现问题，再做最小修改；运行现有前端测试和格式检查，提供修改前后说明，并列出未能验证的部分。不要提交或推送。

“不要提交或推送”也是有效边界。Codex 能修改并不代表应自动发布。你可以先要求本地成果，审查后再单独授权提交。

任务很大时，先使用计划模式拆成可独立验收的阶段。不要把“重新设计整个产品、迁移数据库、补齐测试并发布”塞进一次执行；范围越大，错误越难定位，差异也越难审查。

## 29.5 Git 记录的不是文件，而是变化

Git 是版本控制系统。可以先掌握六个概念：

- **仓库**：被版本管理的项目；
- **工作区**：你当前看到和正在修改的文件；
- **暂存区**：准备放进下一次提交的变化；
- **提交**：带说明的一组历史记录；
- **分支**：一条可以独立推进的变化线；
- **差异（diff）**：两个状态之间具体改了什么。

一个文件可以同时包含已暂存和未暂存修改，这是正常现象。提交前看 `git status` 确认范围，再看 diff 理解每一处变化。不要为了方便使用“全部暂存”，把日志、临时文件、密钥或他人的修改一起提交。

提交应该表达一个清楚目的，例如“修复移动端报名表溢出”，而不是“更新文件”。相互独立的变化分开提交，之后审查、回退和定位问题都会更容易。

分支适合把一项工作与稳定主线隔开。worktree 可以为不同分支建立独立目录，让并行任务不直接覆盖当前工作区。它们提供隔离，但合并前仍要处理内容冲突并运行完整检查。

## 29.6 在 Codex 中查看和整理差异

桌面端的 review pane 可以查看当前 Git 仓库中的变化，包括 Codex、你本人或其他工具产生的未提交修改。它不是只显示“AI 改了什么”。

你可以按未暂存、已暂存、提交、分支或最近一轮查看差异，对单个文件或代码块暂存、撤销，也可以留下行内意见。撤销是破坏性动作：如果不确定某段变化属于谁，先查看历史和状态，不要直接恢复整个文件。

审查时不要只看绿色和红色行数。逐项问：变化是否对应任务；有没有顺手重构无关内容；错误处理和边界条件是否保留；文案、配置和依赖是否合理；有没有意外加入生成文件或敏感信息。

对看不懂的差异，可以让 Codex 用用户行为解释：“这段变化会让页面发生什么不同？删除它会怎样？有没有更小方案？”理解影响比逐行背语法更重要。

## 29.7 测试不是一句“应该可以”

可靠验证要分层进行。

第一层是静态检查，如格式、类型、链接和配置校验；第二层是自动测试，确认已有行为没有被破坏；第三层是针对本次任务的实际操作，例如打开页面、导入样例数据、生成文件并检查输出；高风险修改还需要人工复核或在测试环境试运行。

Codex 可以使用集成终端运行项目命令，也能读取当前终端输出，帮助分析构建或测试失败。常见命令包括 `git status`、项目测试和 lint，但真正命令应以项目文档或 `AGENTS.md` 为准。

测试通过不代表需求一定实现。测试可能覆盖不足；需求也可能写错。最终报告应同时说明运行了什么、结果是什么、哪些没有运行、为什么没运行。不要接受只有“已完成”的交付。

如果检查失败，先区分是本次修改造成、环境原本损坏，还是依赖外部服务。保留错误证据，修复后重新运行相关检查；不要通过删除测试或放宽规则来制造绿色结果。

## 29.8 让审查独立于实现

实现者容易沿着自己的思路检查，独立审查能从不同角度寻找问题。在支持的界面中，`/review` 可以审查未提交修改、某个提交或相对基础分支的变化，并给出带优先级的发现，而不直接修改工作区。

审查提示应说明范围和标准，例如：“审查当前未提交变化，重点检查数据丢失、权限绕过、移动端回归和缺少测试；只报告可操作问题，附文件位置和复现条件，不修改文件。”

收到发现后，不要机械地全部接受。要求证据，判断是否真实、是否在范围内，再让 Codex 修复确认的问题。修复后重新看 diff 和测试，避免一个修复引入新的变化。

审查也适用于文档、配置和数据脚本。失效链接、错误日期、危险默认值和隐私泄露都可能比语法问题更严重。

## 29.9 从任务到提交和协作

团队协作需要让“为什么”与“改了什么”关联起来。一个实用链路是：用 issue 或任务记录目标和验收标准；在独立分支完成最小修改；运行验证；审查差异；创建清晰提交；再通过 pull request 让他人复核。

提交说明回答“这一组变化做了什么”。Pull request 还应说明背景、方案、测试结果、已知限制和风险。不要把整段聊天记录当成说明；提炼真正影响决策的信息。

Codex 可以协助整理 issue、生成变更摘要、回应审查意见和准备提交，但对外创建分支、提交、推送或合并都会改变共享状态，应符合你的明确授权和团队流程。保护分支、必需检查和人工批准仍然有效。

如果多人或多个智能体同时工作，要提前划分文件和职责。合并顺序、接口约定和共同验证由主负责人协调。出现冲突时，理解双方意图再解决，不要仅选择“保留一边”。

## 29.10 安全边界与恢复思维

项目目录可能包含环境变量、凭证、客户资料和部署权限。不要把 `.env`、token、私钥或真实敏感数据交给不必要的任务，更不能把它们提交到仓库。网络访问、包安装和外部脚本都应遵循最小权限。

执行删除、迁移数据库、覆盖生成物、强制推送或部署生产环境前，先确认目标和恢复方式。Git 可以恢复已记录文件，却不能自动撤回已经发送的邮件、删除的云端数据或泄露的密钥。

养成“可恢复”设计：小步提交、重要数据备份、先在测试环境验证、外部行动保留确认点。风险越高，越应把生成、审查和执行拆开。

## 29.11 一个可复制的完整实践

选择一个已有 Git 仓库中的小任务，例如给静态网站增加“最后更新日期”。分三轮完成：

第一轮只读：

> 只读检查项目，找出页面内容、样式、测试和项目规则。说明实现“显示最后更新日期”的最小方案，并列出当前未提交修改。不要改文件。

第二轮执行：

> 按已确认方案实现，只修改必要文件，不引入新依赖。日期来源必须明确，样式在手机和桌面上都不遮挡正文。运行项目已有检查，展示 diff 摘要和测试结果，不提交、不推送。

第三轮审查：

> 审查本次未提交变化，重点检查日期是否会过期、时区是否明确、页面是否可访问，以及是否混入无关修改。只报告有证据的问题。

预期成果包括：可见功能、有限差异、验证记录和审查结果。验收时亲自打开页面，检查日期来源与格式，确认 Git 状态只包含预期文件。确认无误后，再让 Codex 暂存指定文件、创建清晰提交；是否推送由你单独决定。

## 29.12 常见误区

**会生成代码就等于会交付项目。** 交付还包括理解、验证、审查和记录。

**测试通过就一定没问题。** 测试只能证明被覆盖的条件，不能替代需求验收。

**Git 会自动保护所有内容。** 未记录文件、外部数据和强制操作仍可能无法恢复。

**提交越大越省事。** 大提交更难审查，也更难安全回退。

**Codex 修改的内容都属于同一个任务。** review pane 反映整个工作区，可能混有用户或其他工具的变化。

## 29.13 本章小结

代码工作最可靠的路径是：先理解项目，把需求写成可验收变更，做最小修改，运行分层验证，审查完整差异，再用 Git 记录和协作。Codex 可以贯穿整个过程，但不能替代范围判断、权限边界和最终责任。

> 不必先成为程序员才使用 Codex；但要学会看结果、看差异、看证据，再决定是否让变化进入真实世界。
