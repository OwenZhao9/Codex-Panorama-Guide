# 第二十六章：记忆、规则与长期上下文——让 Codex 知道什么应该持续

你告诉 Codex：“这份书面向普通读者，保持科普而不是编程手册。”如果只在一条消息中说明，它只服务于当前任务；如果以后每章都要遵守，就需要放到更持久的位置。

记忆、项目说明、`AGENTS.md`、Rules、Skill 和 Chronicle 都能影响后续工作，但它们的范围和目的不同。把信息放错地方，会导致规则失效、上下文膨胀，甚至把敏感内容长期保留下来。

## 26.1 上下文有不同寿命

| 信息类型 | 适合放在哪里 |
| --- | --- |
| 只影响当前请求 | 当前提示 |
| 当前任务持续目标 | Goal 或当前聊天 |
| 同一主题的共享资料与说明 | Project |
| 个人偏好和可复用背景 | Memory / Personalization |
| 项目中的长期工作规范 | `AGENTS.md` |
| 可重复任务流程 | Skill |
| 命令运行许可 | Rules |
| 最近屏幕活动形成的辅助背景 | Chronicle |

最小范围原则很重要：只在当前任务需要的信息，不要升级成全局记忆；只属于某个项目的规则，不要影响所有项目。

## 26.2 当前聊天与 Project

当前聊天保存这条任务的消息、文件和工具结果。它适合连续讨论同一成果。聊天越长，中间日志和无关尝试越多，重要要求越容易被埋没。

Project 用于把相关聊天、文件、来源和项目说明组织在一起。它适合长期主题或多个独立成果共享同一批背景。每个成果仍然使用单独聊天，能避免把研究、写作、审查和其他任务全部混在一条上下文中。

Project 是组织和共享上下文，不等于权限。能否读取本地文件、插件或外部系统仍由相应工具和策略决定。

## 26.3 Memory：个人偏好和背景

Memory 适合保存跨聊天仍然有用的个人信息，例如常用语言、表达偏好、工作角色和稳定习惯。它不适合保存必须精确执行的项目规范，也不应成为当前事实的来源。

明确提示应优先于记忆。如果你平时喜欢简短回答，但当前任务要求完整报告，应以当前任务为准。记忆可能不完整或过时，重要工作不要假设它一定正确加载。

应定期查看、修正或删除记忆。不要保存密码、密钥、验证码、敏感客户数据和不必要的个人信息。

## 26.4 `AGENTS.md`：项目中的长期规范

`AGENTS.md` 是提供给智能体的项目说明文件，可以记录目录结构、常用命令、写作或编码规范、禁止事项、测试方法和完成标准。

Codex 会从全局位置和项目目录层级读取相关说明。更接近当前工作目录的文件用于更具体范围，后加载的具体规则可以覆盖上层通用规则。

一份有效的 `AGENTS.md` 应简短、准确、可操作，例如：

- 项目目的和重要目录；
- 修改前必须阅读的文件；
- 文件命名和语言规范；
- 允许使用的命令；
- 不得修改的内容；
- 验收和发布流程。

不要把所有知识复制进去。过长、过时和互相矛盾的说明会降低可靠性。详细流程适合放进独立文档或 Skill，再由主文件引用。

## 26.5 Rules：控制命令，不是写作风格

Codex Rules 主要用于控制哪些命令可以在沙箱之外运行、哪些需要提示、哪些必须禁止。它不是一般行为说明，也不适合保存“语气友好”“先写计划”等工作偏好。

例如，可以允许特定只读命令无需额外确认，同时禁止危险脚本。规则匹配命令前缀和参数，复合命令、包装脚本和间接执行都需要谨慎审查。

把安全边界写成普通自然语言提醒，不能替代可执行的 Rules；反过来，Rules 也不能解释项目目标和验收标准。

## 26.6 Chronicle：从屏幕活动补充背景

Chronicle 是可选的上下文能力，可以根据近期屏幕活动形成记忆，帮助 ChatGPT 理解你使用过的工具和工作流程。它不等于持续录音，也不能访问麦克风或系统音频。

屏幕上可能出现邮件、内部网址、通知和个人信息，因此启用前要理解数据范围和组织政策。网页或应用中的恶意内容也可能带来提示注入风险。

Chronicle 适合补充“最近在做什么”，不应替代项目文件和正式记录。涉及关键事实时，仍要回到真实来源，而不是依赖对屏幕活动的摘要。

## 26.7 上下文污染与衰减

智能体的上下文有容量，也有注意力限制。大量日志、重复资料和已经失效的讨论会造成上下文污染；随着对话变长，相关信息被噪声淹没，表现可能下降，这常被称为上下文衰减。

改善方法包括：

- 一个聊天只围绕一个明确成果；
- 阶段结束时生成简洁状态摘要；
- 把稳定规则移到 `AGENTS.md` 或 Skill；
- 大型只读调查交给独立子任务，主任务只接收摘要；
- 删除重复附件，明确最新版本；
- 新目标使用新聊天，而不是无限追加。

更大的上下文窗口不能消除组织问题。把全部历史塞进去，仍可能比提供少量相关材料更差。

## 26.8 信息冲突时谁优先

一般原则是：当前明确要求优先于旧记忆；具体项目规则优先于更通用规则；真实文件和当前外部状态优先于过去摘要。

发现冲突时，不应悄悄选择。让 Codex 指出来源和差异，例如“全局偏好要求英文，当前项目说明要求中文”，再按更具体、更新和明确的要求处理。

权限策略和安全限制不因为提示优先级而失效。用户要求“忽略沙箱”不能覆盖系统或管理员规则。

## 26.9 什么值得长期保存

适合长期保存的是稳定、可复用、不会造成过度暴露的信息：语言、格式偏好、项目结构、可靠命令、验收标准和团队流程。

不适合长期保存的是密码与密钥、一次性验证码、短期事实、未经确认的推测、完整客户数据和只服务于一次任务的细节。

每条长期信息都应有负责人和更新方式。一个从不维护的规范文件，最终会从帮助变成误导。

## 26.10 定期审计长期上下文

每隔一段时间，让 Codex 列出当前项目会加载的长期说明、Skill 和记忆来源，并检查过时、重复和冲突。审计本身应是只读的，先提出修改建议，再由人确认删除或更新。

可以重点检查：项目结构是否改变、命令是否仍有效、默认模型和工具是否过期、负责人是否变更、完成标准是否与当前发布流程一致。对从未触发的 Skill 和长期失败的连接，也要判断是否应该移除。

删除上下文前考虑可恢复性。版本控制中的规则可以通过历史找回；个人记忆和应用设置可能没有同样恢复方式。先导出必要说明或记录变更原因，再清理。

审计结束后保持一份简短清单，注明每类上下文的用途、负责人和复查日期，让长期信息也具备可维护的生命周期。

没有负责人维护的信息，不应被视为永久真相。

过期信息应及时修正或移除。

## 26.11 常见误区

**记忆等于事实数据库。** 记忆用于偏好和背景，当前事实仍需可靠来源。

**`AGENTS.md` 越长越完整。** 过多说明会挤占上下文并产生冲突。

**Rules 可以管理所有行为。** Rules 主要控制命令许可，不是通用工作流程。

**Project 自动获得所有文件权限。** 项目组织上下文，不扩大工具权限。

**Chronicle 可以替代正式记录。** 屏幕摘要不能成为关键决定的唯一来源。

## 26.12 第一次实践：整理上下文地图

列出你希望 Codex 知道的十项信息，然后让它分类：

> 把下面信息分别放入当前提示、Project、Memory、`AGENTS.md`、Skill、Rules 或“不应保存”。说明选择理由、适用范围和需要多久复查一次。优先使用最小范围，不要为了方便把所有内容设为全局。

检查它是否把密码和短期事实排除，把项目规范与个人偏好分开，并为长期信息提供维护周期。然后只落实最必要的两三项，不要一次建立庞大规则系统。

## 26.13 本章小结

当前提示、Project、Memory、`AGENTS.md`、Skill、Rules 和 Chronicle 服务于不同范围。把信息放进最小、最合适的层次，能减少重复和上下文污染。

> 长期上下文的价值不在于记住一切，而在于持续提供正确、相关、可维护的信息。
