# 第二十五章：Skill 与 MCP——工作方法和外部能力

假设你每周都要制作同一种项目简报：先读计划和会议记录，找出变化，再按固定模板生成报告。流程可以写成 Skill。可是，如果材料位于网盘和协作平台，Skill 本身并不会凭空读取它们，还需要连接外部工具的 MCP。

一句话概括：**Skill 主要告诉 Codex 怎样做，MCP 主要让 Codex 能够调用什么。**

## 25.1 Skill 是什么

Skill 是面向特定任务的可复用工作流程。它可以包含名称、触发说明、完整步骤、模板、参考资料和可选脚本，使 Codex 在每次遇到同类任务时遵循一致方法。

一个 Skill 通常以目录存在，核心是 `SKILL.md`。名称和 description 帮助 Codex 判断何时使用，正文说明实际流程；额外目录可以保存模板、示例、参考文档和脚本。

Skill 不是一段永久塞进所有聊天的超长提示。Codex 先看到简短名称与描述，只有选择该 Skill 时才读取完整说明，这种方式称为渐进式披露，可以减少无关上下文。

## 25.2 什么时候应该创建 Skill

适合固化为 Skill 的任务通常：

- 会重复出现；
- 输入与输出结构相对稳定；
- 好结果依赖一套明确步骤；
- 有模板、品牌规范或检查表；
- 多个人需要遵循同一方法；
- 手工提示经常漏掉相同步骤。

例如周报、会议跟进、演示文稿检查、数据质量评估和发布前审查都适合。

一次性任务、目标仍在探索的任务和需要大量临场判断的工作，不必急着创建 Skill。先通过几次真实执行把方法跑通，再固化更可靠。

## 25.3 一个好 Skill 的组成

### 清楚的触发范围

description 应说明何时使用、何时不要使用。范围过宽会在无关任务中触发，范围过窄则很难被发现。

### 面向结果的步骤

写明输入、主要阶段、输出和完成标准，而不是只写“认真分析”“保持专业”。每一步都应有实际作用。

### 必要资源

模板、样例、术语、品牌规则和检查表可以作为参考文件。主说明保持简洁，需要时再读取具体资源。

### 可验证输出

说明最终文件、字段、报告结构和检查方式。Skill 的价值是提高一致性，不是只让提示变短。

### 安全边界

如果流程可能发送、发布、删除或修改外部数据，应明确人工确认点和允许范围。

## 25.4 Skill 怎样触发

Codex 可以在任务与 description 匹配时自动选择 Skill，也可以由用户显式指定。在 CLI 和 IDE 中通常使用 `$` 选择 Skill，ChatGPT 相关界面可能通过 `@` 或能力选择器调用。

自动触发依赖描述质量。如果安装了大量 Skill，初始列表还可能为了控制上下文而缩短或省略部分描述。因此，关键用途和触发词应放在 description 前面。

显式指定适合你已经知道必须遵循某个流程的情况；隐式选择适合让 Codex 根据任务自动路由。重要任务可以直接点名，减少歧义。

## 25.5 MCP 是什么

MCP，即 Model Context Protocol，是让 ChatGPT 或 Codex 连接外部工具和信息的协议。MCP server 可以提供工具、资源和提示，并负责认证、结构化输入输出以及对目标系统执行操作。

它可以连接项目管理、数据库、设计工具、浏览器、文档系统和内部服务。与直接复制文本相比，MCP 能提供实时数据和可执行动作；与 Computer Use 点击界面相比，结构化工具通常更稳定、可重复，也更容易验证。

MCP 只是连接标准，不代表连接的服务天然安全或高质量。你仍然要信任服务器、检查权限、理解数据流，并限制工具范围。

## 25.6 Skill 和 MCP 怎样配合

最典型组合是：Skill 定义流程，MCP 提供步骤需要的能力。

例如“每周客户反馈简报”Skill 可以规定：读取最近七天反馈、去重、分类、寻找高频问题、生成摘要并核对来源。相应 MCP 则连接客服系统和项目跟踪工具，负责读取反馈和创建经过确认的任务。

如果只有 MCP，智能体知道有哪些工具，却未必按照团队标准使用；如果只有 Skill，它知道怎样工作，却可能拿不到真实数据。两者组合后，流程和能力才完整。

## 25.7 什么时候不需要 MCP

任务材料已经在当前文件夹、聊天附件或项目中，并且不需要外部实时数据和行动时，普通文件工具就够了。为了读取一个本地表格而安装远程 MCP，只会增加认证和故障点。

同样，如果外部系统已有受支持插件，优先使用经过打包的现成连接，通常比手动配置 MCP 更方便。只有现有能力不能满足需求、组织有内部服务或需要自定义工具时，才考虑直接配置。

选择顺序可以是：当前上下文 → 已安装插件 → 可信 MCP → Browser/Computer Use。越往后越要考虑维护和权限。

## 25.8 创建 Skill 的基本流程

1. 选择一个已经重复过的具体任务；
2. 收集一份成功结果和常见失败；
3. 写明输入、步骤、输出、边界和验收；
4. 先做 instruction-only Skill，确有必要再加入脚本；
5. 用真实样例测试正常情况和缺失输入；
6. 根据结果缩小范围、补充检查；
7. 需要团队安装和连接工具时，再打包为插件。

可以使用内置 `skill-creator` 帮助创建，但生成结果仍要人工审查。Skill 中的脚本会执行真实操作，必须像审查代码一样检查来源和副作用。

## 25.9 配置 MCP 时检查什么

无论使用本地 STDIO server 还是远程 HTTP server，都应确认：

- 服务器来源和维护者；
- 认证方式及凭据保存位置；
- 暴露哪些工具和数据；
- 工具是只读还是可以写入；
- 请求发送到哪些域名；
- 失败、超时和重复调用怎样处理；
- 日志是否可能包含敏感信息。

先测试只读工具，再测试可恢复的写入。对发送、支付、删除和权限修改保留审批，不要因为工具返回结构化 JSON 就降低警惕。

## 25.10 测试和维护 Skill

Skill 至少要测试三种情况：正常输入、缺少关键输入和不应触发的相邻任务。检查它是否按预期选择资源、能否明确停止、输出是否满足模板，以及失败时有没有编造缺失信息。

修改 Skill 后保留版本说明，记录为什么改变和哪些样例通过。团队共享的 Skill 不应由一次偶然结果驱动更新；先确认问题可以重复，再调整说明或脚本。

如果 Skill 越写越长，通常说明范围太大。可以拆成多个聚焦 Skill，或把参考资料移出主说明。稳定、短小、边界明确的 Skill 比覆盖所有情况的“超级 Skill”更容易触发和维护。

测试结果应保留输入、实际输出和失败原因，避免修复一个样例时破坏其他场景。

通过测试后再扩大触发范围或分享给团队。

分享时附上适用边界和已验证样例。

## 25.11 常见误区

**Skill 是一个外部工具。** Skill 主要是流程说明和资源，外部能力通常来自 MCP 或连接器。

**MCP 会告诉智能体最佳做法。** MCP 提供能力，不自动包含团队流程和质量标准。

**任何重复任务都要建 Skill。** 不稳定流程固化以后，只会稳定地产生错误。

**脚本比说明更专业。** 能用清晰指令完成时，instruction-only 更容易审查和维护。

**连接成功就不必测试权限。** 工具可能拥有超出当前任务需要的写入能力。

## 25.12 第一次实践：设计一个不带工具的 Skill

选择一个每周重复的小任务，例如会议纪要整理，输入：

> 帮我设计一个“会议跟进”Skill，暂时不连接外部服务，也不写脚本。输入是会议记录，输出包括决定、待办、负责人、截止时间、未解决问题和需要确认的缺失信息。不得猜测负责人或日期。请给出准确的触发描述、工作步骤、输出模板、验收清单和不应使用该 Skill 的情况。

使用两份不同会议记录测试：一份信息完整，一份缺少负责人和日期。好的 Skill 应稳定输出结构，并在第二份中明确缺失，而不是补写合理猜测。

## 25.13 本章小结

Skill 固化一类工作的步骤、资源和质量标准；MCP 把外部工具与信息接入智能体。重复流程先用 Skill，外部能力按需要使用插件或 MCP，两者可以组合。

> 先把方法跑通，再把它固化；先明确需要什么能力，再扩大连接范围。
