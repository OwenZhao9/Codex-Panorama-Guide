# 第四十章：实战案例七——搭建个人或团队 AI 工作流

前六个案例都完成了一项具体成果。最后一个案例要解决更长期的问题：怎样让这些方法不依赖某个人记住所有提示，也不让团队为了使用 AI 建立一套过度复杂的新制度。

本章以一个五人公益团队为例。团队每周要整理项目进展、研究政策变化、制作对外材料、维护活动网站并跟进任务。目标不是“让 AI 接管团队”，而是建立一套人人看得懂、关键步骤可追溯、重复工作能复用、外部操作有权限边界的协作系统。

## 40.1 从工作地图开始

先盘点团队一个月内反复发生的工作，记录触发条件、输入、负责人、交付物、频率、风险和当前痛点。例如：

| 工作 | 触发 | 输入 | 成果 | 风险 |
| --- | --- | --- | --- | --- |
| 周进展汇总 | 每周五 | 项目表、会议记录 | 一页周报 | 遗漏或误报 |
| 政策监测 | 每周 | 官方网站 | 变化简报 | 过时来源 |
| 活动发布 | 日期确定 | 文案、图片、报名信息 | 页面与素材 | 错误公开 |
| 会议跟进 | 会议结束 | 纪要 | 决定、负责人、日期 | 私密信息 |
| 网站维护 | 内容变更 | 已批准资料 | 新版本 | 生产故障 |

接着区分四类工作：一次性思考、可复用流程、适合定时运行、必须由人决定。不是每项任务都要做成 Skill 或自动化。第一次做、判断高度依赖情境的任务，先在普通聊天中完成；步骤已经稳定但每次输入不同的任务适合 Skill；按时间或事件重复的稳定流程才考虑 Scheduled task；人员、资金、承诺和公开发布保留人工决策。

## 40.2 设计最小信息架构

团队可以建立一个共同 Project，保存组织简介、受众、项目清单、写作规范、已批准模板和共享来源。每个独立成果使用单独聊天，例如“七月周报”“活动页改版”“政策变化研究”。Project 提供共同背景，聊天保持结果清晰。

本地共享文件可以采用：

```text
ai-workflow/
  README.md
  AGENTS.md
  context/
    organization.md
    audience.md
    glossary.md
  playbooks/
    weekly-update.md
    research-standard.md
    publishing-checklist.md
  templates/
  decisions/
  outputs/
  .agents/skills/
```

`README.md` 告诉成员这里有什么；`AGENTS.md` 告诉 Codex 在该项目中怎样工作；`context/` 保存相对稳定的事实；`playbooks/` 保存人也能阅读的流程；Skill 只承载确实需要重复调用的工作方法。不要把所有信息塞进一个巨大文件，否则过期规则会污染每个任务。

## 40.3 把稳定规则写进正确位置

一次任务的受众、日期和边界写在当前提示中。跨聊天共享的组织背景和文件放在 Project 中。适用于本地项目的命名、目录、检查和发布规则写入 `AGENTS.md`。个人偏好放在个人设置或全局指导，不应悄悄成为团队政策。

这个团队的 `AGENTS.md` 可以包含：

- 修改前先盘点相关文件和最新版本；
- 未经明确要求，不发送、发布、部署或删除；
- 当前事实必须标注来源和核对日期；
- 个人资料只用于被授权的任务，不写入公开输出；
- 生成文件放入约定目录并报告路径；
- 完成前检查链接、数字、名称、日期和格式；
- 遇到冲突信息时停止猜测，记录冲突和需要的决定。

保持简短、可执行。Codex 在运行开始时读取指导；不同目录可以有更具体的文件，离当前工作目录更近的指导优先。规则若只是愿望，例如“永远做到最好”，无法帮助验证。每次重复错误后复盘，才添加真正能防止问题的规则。

## 40.4 把重复方法做成 Skill

选择“周进展汇总”作为第一个 Skill，因为它每周重复、输入相似、格式稳定、风险可控。Skill 说明：何时使用、需要哪些输入、怎样找决定和行动项、怎样处理冲突、输出模板、不得执行的动作和验收方法。

Skill 可以附带一份周报模板和一个检查清单。运行时输入本周日期范围、项目状态和会议记录，输出一页周报草稿。先用三组真实但去敏的数据测试：正常一周、缺少负责人和日期的一周、两个来源互相冲突的一周。只有三个场景都得到可审查结果，才安装给团队使用。

如果现有插件已经提供同类稳定流程，优先评估和安装，而不是重复建设。自建 Skill 适合团队独特的方法；插件适合需要安装、分发、连接服务或组合多个 Skill 的能力。无论来源如何，都要检查说明、权限、依赖和维护者。

## 40.5 用插件和 MCP 接入外部系统

团队的计划可能在 Drive，讨论在 Slack，任务在项目管理工具。仅靠复制粘贴会丢失版本，也增加敏感信息扩散。若工作区允许，可以通过插件或 MCP 连接这些来源。

连接前先写一张数据流图：Codex 从哪里读取什么信息，会生成什么，是否会写回，谁能批准。读取项目计划与创建任务是不同权限；在 Slack 搜索历史与发送消息也是不同权限。首版工作流只读获取上下文并生成本地草稿，确认稳定后再考虑有限写入。

MCP 是外部工具和上下文的连接方式，能够提供读取资源和执行操作。Skill 负责“按什么流程做”，MCP 负责“从哪里读、能对哪里行动”。配置完成不代表任意工具都应自动批准。敏感连接应限制可用工具、保持必要的确认，并定期检查授权是否仍然需要。

Web 端的托管插件、桌面或 CLI 的本地 MCP 配置可能不同，团队文档要写清在哪个界面运行。若成员看不到某工具，先检查插件是否安装启用、连接是否授权、工作区管理员是否允许、是否需要重启或新建任务，不要直接假设提示写错了。

## 40.6 给自动化设置人类责任人

团队把已试跑的周报 Skill 安排为每周五下午生成草稿。Scheduled task 的提示写明时间窗、输入来源、输出格式、缺失信息处理和禁止发送。每次运行由运营负责人审阅，确认后才复制到团队频道。

每项自动化都要有：业务负责人、技术或配置负责人、运行位置、输入、输出、权限、失败通知、复核频率和停止条件。没有负责人的自动化最终会成为没人敢关、也没人相信的系统。

自动化使用最小权限。Web 任务不能直接访问个人电脑文件；桌面本地任务需要机器开机、应用运行和项目可用；无人值守任务不能指望临时审批。若任务需要高风险动作，应拆成“自动准备建议”和“人工批准执行”两步。

## 40.7 为复杂工作设置主任务和检查点

活动发布等跨多天任务可以使用 Goal 持续推进，主任务保存目标、交付物、依赖、决策和完成标准。研究、视觉、页面检查等相对独立的工作可以拆分，但主任务必须统一事实和最终验收。

设置三个决策门：

- 方向门：受众、目标、范围和成功标准确认；
- 成果门：内容、数据和设计达到可审查状态；
- 行动门：发布、发送、部署或写回外部系统前再次确认。

Goal 让任务持续，不会自动扩大权限，也不会替人作重大决定。状态汇报只回答已完成、证据、下一步、风险和需要的决定，避免用大量过程文字掩盖真正的阻塞。

## 40.8 建立统一验收和证据习惯

团队为所有成果采用一张最小验收卡：

- 正确性：事实、数字、链接和计算是否核验；
- 完整性：约定成果与边界是否全部覆盖；
- 一致性：名称、日期、术语和版本是否统一；
- 可用性：目标读者能否顺利阅读或完成任务；
- 安全性：权限、隐私、公开动作和回退是否明确；
- 证据：检查结果、预览、测试或来源在哪里。

不同成果再加专门检查：报告查引用；表格查公式和原始层；演示查页面渲染；网站查浏览器行为；自动化查运行历史和失败路径。让另一个聊天独立审查高影响成果，避免原任务只验证自己预期的成功路径。

“Codex 说已经检查”不是证据。证据应是可复算数值、可访问链接、文件预览、测试输出、运行记录或明确的抽样结果。

## 40.9 用四周完成团队试点

第一周只做工作盘点和一个共同 Project，不安装大量工具。第二周完成 `AGENTS.md`、周报模板和第一次人工运行。第三周把周报做成 Skill，并连接一个只读来源。第四周再创建定时草稿任务，审查前三次运行。

试点指标包括：交付耗时、人工返工、事实错误、漏项、成员采用率、权限请求、失败恢复时间和成员是否理解结果从哪里来。效率提高但错误增加，不算成功；只有一位“AI 专家”会运行，也不算团队系统。

每月清理过期 Project 来源、旧模板、无主自动化和不再使用的连接。每季度复查权限、Skill 版本、团队规则和高风险流程。变更要有记录，让成员知道为什么规则改变。

## 40.10 可直接复制的启动提示

```text
请帮助我们为一个五人公益团队设计最小可行的 AI 工作流。

先只读盘点过去一个月的重复工作、现有文件、沟通工具、模板和审批方式。建立工作地图，记录触发、输入、负责人、成果、频率、风险和痛点。不要先安装工具或创建自动化。

把工作分为：一次性任务、可复用 Skill、适合 Scheduled task、必须人工决定。为推荐的系统设计 Project 与本地目录结构、简短 AGENTS.md、一个“周进展汇总”Skill 草案、外部连接数据流图、权限表、验收卡和四周试点计划。

默认只读外部来源，只生成草稿；未经确认不得发送消息、创建外部任务、部署、删除或公开内容。个人资料和内部信息遵守最小使用原则。任何连接都说明读取与写入权限、授权人和停用方法。

先提交架构和取舍，确认后再创建文件。完成前用正常、缺失信息和来源冲突三个场景测试周报流程，并说明测试证据、已知限制、负责人和停止条件。
```

## 40.11 本案例的能力边界

AI 工作流不能修复本来就混乱的责任、数据和审批制度。Codex 能把规则执行得更稳定，也会把错误规则更稳定地放大。团队必须决定谁对事实、决定、权限和对外行为负责。

不要以连接数量衡量成熟度。一个清楚的 Project、一份短 `AGENTS.md`、一个经过测试的 Skill 和一项有负责人的自动化，往往比十个未经治理的插件更有价值。最好的工作流不是最自动，而是成员知道它怎样工作、何时信任、如何验证、哪里必须停下来由人判断。

至此，本书已经从认识 Codex、配置环境、理解核心能力，走到标准工作流和综合实战。你真正要带走的，不是一套固定按钮，而是一种新的工作方法：定义结果，提供上下文，选择合适能力，保持过程可观察，用证据验收，并把成熟方法沉淀下来。
