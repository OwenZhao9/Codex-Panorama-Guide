# 第二十四章：应用、插件与连接器——把外部世界接入工作流

你要准备每周项目更新：计划在网盘，讨论在 Slack，会议在日历，客户回复在邮箱。让 AI 只根据聊天内容写周报，它看不到真正发生了什么；把每个系统的数据手工复制进来，又失去了自动化价值。

应用、插件和连接器解决的是同一个大问题：让 ChatGPT 或 Codex 在得到授权后使用外部信息和工具。但它们位于不同层次，不能简单当成同义词。

## 24.1 三个概念怎样区分

### 连接器（Connector）

连接器把 ChatGPT 与 Google Drive、Slack、GitHub、邮箱或其他服务连接起来。它处理登录和授权，并提供读取信息或执行操作的工具。连接器背后通常由 MCP server 提供结构化能力，也可以带有专门界面。

### 插件（Plugin）

插件是可以安装的能力包。它可以只包含 Skill，也可以包含连接器、MCP server、浏览器扩展、Hook、资源和定时任务模板。插件的价值是把完成一类工作的说明与所需工具一起分发。

### 应用（App）

应用通常指基于 MCP 的集成，可以只提供工具，也可以通过 Apps SDK 提供专门的 ChatGPT 界面。对普通使用者而言，应用强调“用什么外部服务完成工作”，插件强调“安装一整套可复用能力”。

可以记住：连接器负责接通服务，Skill 负责告诉智能体怎样工作，插件负责把它们打包，应用可以在此基础上提供完整交互体验。

## 24.2 插件能包含什么

一个插件可能包含：

- 可复用工作流程的 Skill；
- 连接 GitHub、Drive、Slack 等服务的 Connector；
- 提供结构化工具的 MCP server；
- 网页操作所需的浏览器扩展；
- 在特定生命周期运行的 Hook；
- 自动化使用的定时任务模板；
- 模板、参考资料和展示资源。

并不是每个插件都有全部组成部分。安装前先看它实际包含什么、需要哪些权限、由谁维护、数据会发送到哪里。

## 24.3 当前可用界面

截至 2026 年 7 月 18 日，插件可用于 ChatGPT web 的 Work、桌面应用中的 Work 与 Codex，以及 Codex CLI。插件目前不在普通 Chat mode、IDE Extension 和移动端中提供。

安装以后通常需要开始新任务或新 CLI session，相关 Skill 和工具才会进入环境。如果插件带连接器，还可能在安装时或首次使用时要求登录外部服务。

界面没有出现插件，不一定是插件本身损坏。还要检查账号方案、工作区管理员设置、插件是否安装并启用、连接器是否授权，以及当前使用的界面是否支持。

## 24.4 能力真正可用需要经过多层

一个插件显示“已安装”，不代表所有能力都已经可用。完整链路可能包括：

1. 插件在当前环境可见并启用；
2. 所需 Skill 成功加载；
3. 连接器或 MCP server 正常连接；
4. 外部账号完成认证；
5. 当前账号拥有目标数据权限；
6. 工作区策略允许该能力；
7. 当前任务批准了实际操作。

排查问题时按这条链路逐层检查，比反复要求 AI“再试一次”更有效。

## 24.5 外部权限不会被绕过

连接器只能看到当前用户或服务账号本来有权访问的内容。ChatGPT 登录成功，不会自动获得整个公司网盘、其他人的邮件或受限仓库。

外部服务的身份权限、ChatGPT 工作区策略、Codex 沙箱和具体行动审批是不同边界。允许连接 Drive，不等于允许公开分享文件；允许读取邮件，不等于允许发送；允许访问 GitHub，不等于允许合并代码。

提示中仍应写明行动边界：

> 使用 Drive 和 Slack 中与“秋季发布”项目有关的资料起草周报。只读取，不修改来源；如果发现冲突，列出两种说法。生成草稿后停止，不要发送或发布。

## 24.6 数据会经过哪里

使用连接器时，相关请求和必要上下文会发送给连接服务，外部服务的条款和隐私政策也会适用。不要只看 ChatGPT 的权限提示，还要理解插件提供方、MCP server 和目标系统分别处理什么数据。

对敏感任务，至少确认：

- 谁开发和维护该插件；
- 连接的是哪个域名和服务；
- 使用什么账号认证；
- 请求会包含哪些聊天、文件或字段；
- 工具可以读、写、发送还是删除；
- 日志和数据保留怎样管理；
- 工作区管理员是否批准。

不要向不需要某项数据的工具发送整份文档。最小权限也包括最小上下文。

## 24.7 怎样选择合适插件

先从结果出发，而不是从插件数量出发。问自己：任务缺少的是工作方法、数据来源还是外部行动？

- 只缺稳定步骤：使用 Skill；
- 只缺外部数据或操作：使用连接器或 MCP；
- 两者都需要，并希望方便安装分享：使用插件；
- 需要专门交互界面：考虑应用。

优先选择来源明确、权限范围清楚、与你的真实任务直接相关的插件。安装十个“可能有用”的插件，会增加工具选择、认证和数据暴露面，也会让故障排查更复杂。

## 24.8 安装、使用与移除

安装前查看详情和权限，连接外部服务时确认账号。安装后在新任务中直接描述结果，也可以用 `@` 指定插件或其中能力。

第一次运行采用低风险只读任务，检查它实际访问了什么、返回了什么、有没有请求意外权限。确认稳定后再考虑写入和自动化。

移除插件时要注意：卸载能力包不一定断开其中连接器的账号授权。还应在 ChatGPT 连接设置和外部服务中检查并撤销不再需要的连接。工作区默认安装的插件可能只能由管理员管理。

## 24.9 维护插件与连接

插件不是安装一次就永久不变。提供方可能更新 Skill、增加工具、修改认证或要求新的权限。重要工作流应记录插件版本、连接账号、允许的操作和最近测试时间。

更新后先重新运行只读测试，并检查权限提示是否变化。新增写入工具不应因为旧版本已经受信任就自动放行。团队环境中，由明确负责人决定哪些插件可以安装、哪些连接器可以使用，以及出现问题怎样撤销。

故障排查可以按症状定位：插件找不到，先检查界面与安装状态；工具存在但不能用，检查新任务是否加载和 MCP 是否连接；能调用但没有数据，检查外部账号权限；能读取但不能写入，检查工具能力、服务权限和任务审批。

定期清理不再使用的插件、连接和 token，可以减少攻击面。移除后还应检查自动化或 Skill 是否仍引用旧能力，避免定时任务在后台持续失败。

权限可以分阶段扩大。第一阶段只搜索和读取，第二阶段允许创建草稿或测试记录，第三阶段才开放经过确认的真实写入。每个阶段都保留来源和操作日志，并验证外部系统的最终状态。这样即使插件行为与预期不同，影响也被限制在较小范围。

对多人共用的连接，不要依赖某个员工的个人账号长期支撑关键流程。应明确账号所有者、离职或授权失效时的处理方式，以及自动化失败由谁收到通知。

如果插件停止维护或权限说明不清，应准备替代方案，例如回到只读导出文件、使用官方连接器，或暂时改为人工确认。关键业务不应只有一条无法审计的外部依赖。

替代流程也应定期测试，不能只存在于说明文档中。

把最近一次成功测试的日期、使用账号和输出位置写进维护记录，交接时就不必重新猜测整条数据链路。

## 24.10 常见误区

**插件就是一个连接器。** 插件可以包含连接器，也可以只包含 Skill 或其他能力。

**安装以后当前任务立即可用。** 新能力通常需要新任务或 session 加载。

**登录成功代表能看全部数据。** 外部系统原有权限仍然生效。

**卸载插件会自动撤销所有授权。** 连接器可能保持连接，需要单独管理。

**插件越多，AI 越强。** 无关工具会增加选择成本和风险，未必改善结果。

## 24.11 第一次实践：用连接来源起草周报

选择一个不涉及敏感行动的连接来源，先做只读任务：

> 使用已连接的项目资料，整理过去七天的进展、决定、风险和下一步。每项内容注明来源位置和日期；相互矛盾的信息单独列出。只生成周报草稿，不修改外部记录，不发送消息。完成后说明使用了哪些工具、哪些位置无法访问。

检查来源是否真的属于项目，权限是否符合预期，草稿是否区分事实与推断。只有只读流程稳定以后，再设计更新记录或发送等写入步骤。

## 24.12 本章小结

连接器接通外部服务，Skill 固化工作方法，插件打包可安装能力，应用可以在工具之上增加完整界面。真正能否使用还取决于认证、账号权限、工作区策略和任务审批。

> 安装能力之前先理解数据和权限，连接成功之后仍要控制实际行动。
