# 第十章：Codex CLI 与 IDE Extension

桌面应用适合用图形界面管理项目、文件和审查；CLI 与 IDE Extension 则把 Codex 放到开发者最常停留的位置：终端和编辑器。

这两个入口并不会自动提高模型能力。它们的优势是上下文更贴近项目、反馈链更短、命令和差异更容易验证。即使你不是职业程序员，只要工作依赖批量文件、脚本或版本控制，也可能从 CLI 获益。

## 10.1 CLI 与 IDE 分别适合什么

**Codex CLI** 是终端优先的交互入口。它适合通过文件和命令表达的任务：调查目录、运行脚本、修改项目、执行测试、检查 Git 和接入自动流程。

**IDE Extension** 位于代码编辑器中。它能利用当前工作区、打开文件和选中代码，适合边阅读边解释、边修改边审查。

| 情况 | 优先入口 |
| --- | --- |
| 经常在终端运行命令和脚本 | CLI |
| 需要围绕当前文件或代码选区工作 | IDE Extension |
| 想查看图形化预览、项目和工作树 | 桌面应用 |
| 任务需要无人值守脚本或 CI | CLI 的非交互能力 |
| 只想问问题或制作办公成果 | Chat 或 Work |

CLI 与 IDE 可以同时安装。它们共享许多认证和配置，但不必在第一次就同时学习。

## 10.2 安装 CLI 前的准备

CLI 需要一个可用终端。macOS、Linux 与 Windows/WSL 的 shell 和路径规则不同；项目本身还可能需要 Git、Node.js、Python 或其他工具。

当前常见官方安装方式使用 npm：

```shell
npm install --global @openai/codex
```

安装命令会随发布方式更新，执行前应核对官方 CLI 页面。不要从名称相似的第三方 npm 包或陌生脚本安装。

安装后验证：

```shell
codex --version
```

若终端提示找不到命令，先检查 npm 全局安装目录是否在 `PATH`，不要立刻使用管理员权限重复安装。还可以运行 `codex doctor` 生成本地安装、配置、认证、运行时、Git 与终端等诊断报告。

## 10.3 登录 CLI

第一次运行 `codex` 时，如果没有有效会话，会引导 ChatGPT 登录。也可以显式运行：

```shell
codex login
```

浏览器完成登录后，使用下面命令确认状态：

```shell
codex login status
```

CLI 也支持 API key 登录，但 key 应通过标准输入或安全环境提供，不要直接写进命令历史、配置示例或仓库。API key 使用按 Platform 计费，部分 ChatGPT 云端功能不适用。

退出时使用 `codex logout`。CLI 与 IDE Extension 会共享缓存的登录状态，因此在一边退出，另一边下次也需要重新登录。

## 10.4 从正确目录启动

终端当前目录就是任务的重要上下文。进入项目根目录后再启动：

```shell
cd /path/to/project
codex
```

不要从用户主目录启动后再说“找一下我的项目”。先运行 `pwd` 和 `git status` 确认位置与版本状态。项目含 `.git` 时，Codex 通常将其识别为根，并从相应位置加载 `.codex` 配置和 `AGENTS.md`。

如果任务只针对子项目，可以使用更小工作目录；需要额外目录时，应明确增加必要范围，而不是把整个文件系统开放为可写。

第一次进入陌生仓库时，先只读询问：

> 说明当前工作目录、项目根、已有未提交修改、项目规则和可用检查命令。不要修改文件，不要联网。

## 10.5 交互式 CLI 的基本用法

直接运行 `codex` 会打开终端界面。你可以用自然语言描述任务，不需要把每项工作转换为 shell 命令。

常用斜杠命令帮助控制会话：

- `/permissions`：查看或改变当前权限；
- `/model`：选择当前可用模型与相关设置；
- `/plan`：先进入计划模式；
- `/goal`：启动有完成标准的持续目标；
- `/review`：审查工作区、提交或分支差异；
- `/new`：为不同结果开始新任务。

具体命令会随版本变化，输入 `/` 查看当前客户端实际支持的列表。不要背诵大量命令后才开始；先掌握权限、计划、审查和新任务即可。

提示仍应包含成果、范围和验证。例如：

> 检查 `docs` 中的相对链接，只修复能够由仓库结构证明的错误。不要改正文措辞，不要安装依赖。运行现有文档检查并显示 diff，不要提交。

## 10.6 交互任务与非交互执行

交互模式适合需求会变化、需要观察和追问的工作。CLI 也提供非交互执行能力，适合脚本、批处理和 CI。

非交互任务不会因为没有人在旁边就更安全。它必须拥有更明确输入、固定权限、机器可判断的退出状态和可保存日志。先在交互会话中跑通提示与命令，再放进自动流程。

自动化使用 API key 或企业访问 token 时，应运行在可信私有环境，限制仓库与网络权限。不要把 Codex 执行端点暴露给不可信公众输入，否则提示和命令都可能成为攻击入口。

入门阶段不需要立即学习所有 `codex exec` 参数。先建立“人工可复现—权限最小—失败可见”的流程，再考虑无人值守。

## 10.7 在编辑器中安装 IDE Extension

从受支持编辑器的官方扩展市场安装 OpenAI 发布的 Codex 扩展，确认发布者和扩展详情，不要选择名称相似的第三方插件。

安装后打开一个练习工作区，在扩展面板选择 **Sign in with ChatGPT** 完成浏览器登录；若有明确 API 需求，也可以选择 **Use API Key**。CLI 已登录时，扩展通常可以复用共享认证状态。

不同编辑器和版本的入口位置可能变化。找不到面板时，使用命令面板搜索 Codex；安装后若功能没有出现，重新加载编辑器并确认扩展在当前工作区启用。

## 10.8 给 IDE 正确上下文

IDE Extension 可以引用当前打开文件或选中的代码，但选区不是完整需求。它可能不知道上游接口、测试、用户场景和不能改变的行为。

一个好的 IDE 请求可以是：

> 解释当前选中函数怎样处理空输入，并定位相关测试。只提出最小修改方案，先不要编辑。方案必须保持现有返回类型，并说明需要新增哪些测试。

确认后再让它修改和运行检查。不要只说“优化这段”，因为优化可能意味着性能、可读性、结构或行为，方向并不唯一。

扩展的权限控制通常位于输入区下方。使用 Ask for approval 或受限 profile，检查它是否需要项目外文件和网络。编辑器能访问项目不代表所有工具都应获得全盘权限。

## 10.9 CLI 与 IDE 共享什么

CLI 与 IDE Extension 共享本地 Codex 主目录、认证缓存和主要 `config.toml` 配置。用户默认通常位于 `~/.codex/config.toml`，可信项目可以通过 `.codex/config.toml` 提供项目级覆盖。

这意味着你在 CLI 改变持久配置，IDE 重新启动后也可能受到影响。相反，编辑器自身的 `chatgpt.*` 显示与交互设置属于扩展，不应写进 Codex 的 `config.toml`。

退出 CLI 登录可能让 IDE 下次重新认证；项目规则和 Skill 也会在两个入口间共享。出现“CLI 正常、IDE 不同”时，检查客户端版本、工作目录、扩展设置和是否重新加载，而不是只比较提示文字。

## 10.10 Windows 原生与 WSL

Windows 可以使用原生 Codex 运行 PowerShell，也可以在 WSL2 中使用 Linux 工具链。选择取决于项目实际位置和依赖。

项目主要位于 Windows 文件系统、使用 Windows 工具时，原生模式更直接。项目已经在 WSL 的 Linux home 中，依赖 Linux 脚本和工具时，使用 WSL 更自然。不要在没有必要时频繁跨越两种文件系统；路径、权限、换行和 I/O 性能都可能产生差异。

IDE Extension 支持配置在 WSL 中运行 Codex。启用后重新加载编辑器，并检查终端路径是否为预期 Linux 路径。Windows 原生沙箱与 WSL 的 Linux 沙箱实现不同，但都应保持受限权限。

## 10.11 两个入口不提供什么

CLI 和 IDE 专注本地项目执行，不是所有 ChatGPT 功能的管理中心。

- CLI 和 IDE 不提供 Scheduled 的管理界面；
- 它们不能独立管理 Sites 项目和分析；
- IDE 不提供插件库；
- 内置 Browser 不在 CLI 或 IDE 中使用；
- 文档、演示与图形预览通常在网页或桌面应用更方便。

可以在 CLI 测试脚本、在 IDE 修改代码，再回到桌面查看预览或管理自动化。选择组合时按成果需要，而不是强迫一个入口完成所有工作。

## 10.12 第一次实践：同一任务跑两遍

准备一个小型 Git 练习仓库。在 CLI 中：

> 只读检查 README、项目规则和 Git 状态，说明启动与检查方式。不要修改。

然后在 IDE 中打开同一仓库，选中 README 一段文字：

> 只修改选中段落，使它更清楚，保持事实和链接不变。运行最小文档检查，显示 diff，不提交。

回到 CLI 运行 `/review` 或要求审查未提交变化。检查两个入口是否看到同一工作区、配置和 diff；确认只有预期段落变化，测试结果真实可见。

这个练习能建立“IDE 修改—CLI 验证—Git 审查”的基本链路。

## 10.13 常见故障

**`codex` 命令不存在。** 检查安装是否成功以及 npm 全局目录是否在 `PATH`。

**登录循环或账号错误。** 使用 `codex login status`，退出后以正确工作区重新登录。

**CLI 与 IDE 行为不同。** 对比版本、目录、配置层、权限和扩展重载状态。

**Windows 路径混乱。** 明确项目运行在原生 Windows 还是 WSL，并让编辑器终端处于同一环境。

**命令被沙箱阻止。** 先确认任务是否真的需要越界，使用最小目录或域名权限，不要默认 Full access。

**扩展看不到当前代码。** 确认工作区、文件和选区，重新加载扩展，并在提示中明确引用对象。

## 10.14 本章小结

CLI 把 Codex 放进终端，IDE Extension 把它放到编辑器旁边。可靠上手包括从官方来源安装、使用正确认证、在项目根启动、保持受限权限，并通过 Git、测试与审查验证变化。

> 入口靠近项目只是第一步；真正的效率来自上下文准确、命令可复现和结果可检查。

下一章将整理模型、权限与 `config.toml` 等基础设置，建立一套不过度配置的默认环境。
