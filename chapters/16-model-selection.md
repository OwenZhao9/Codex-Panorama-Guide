# 第十六章：模型选择——不是越强越好，而是越合适越好

你要处理三项工作：从两百份反馈中提取主题、写一份需要判断和表达质量的策略报告、快速检查几十个文件的结构。如果全部使用同一种模型和设置，当然可以工作，但往往不是最有效的选择。

模型选择的意义，不是追逐排行榜上的“最强”，而是让任务的难度、价值、速度和成本与模型的特长匹配。

## 16.1 模型、推理强度和速度不是一回事

使用 Codex 时，经常同时看到模型、智能等级或推理强度，以及 Standard、Fast 等速度选项。它们分别控制不同问题：

| 选择 | 主要决定什么 |
| --- | --- |
| 模型 | 基础能力、风格和任务侧重 |
| 推理强度 | 在一次任务上投入多少分析和检查 |
| 速度模式 | 模型被服务和返回结果的速度 |

换模型不等于开启 Fast；提高推理强度也不等于换成更强模型。一个任务感觉慢，可能是模型较重、推理等级较高、工具步骤很多或环境本身耗时。先分清原因，才知道应该调哪一个选项。

模型也不会改变权限。无论选择哪种模型，都只能访问当前任务允许的文件、网络、插件和应用。

## 16.2 截至 2026 年 7 月的 GPT-5.6 模型

截至 2026 年 7 月 18 日，Codex 推荐的 GPT-5.6 系列主要包括 Sol、Terra 和 Luna。界面、账号方案和工作区策略会影响实际可见选项。

### Sol：复杂开放任务

Sol 适合含糊、困难或价值较高的任务，需要较多判断、分析和成品质量。例如复杂项目改造、深度研究、重要报告和需要精细表达的文档。

它的优势是完整度和打磨能力，但对于规则清楚的大批量提取，未必是最经济的选择。官方建议在不确定时从 Sol 开始；当前默认 Power 设置使用 `gpt-5.6-sol` 配合 Medium 推理。

### Terra：日常全能型

Terra 是偏实用的日常工作模型。它兼顾推理、工具使用和效率，适合多数结构清楚但仍需要判断的任务，例如项目调查、文件审查、常规分析和多步骤执行。

当你不需要 Sol 的全部深度，又不希望只做机械转换时，Terra 通常是合适的工作模型。它也适合作为并行任务中的调查者，把大量材料压缩成主任务需要的结论。

### Luna：清晰、重复、高容量

Luna 适合规则明确、结果形式稳定、可以批量检查的任务，例如提取字段、分类、格式转换和结构化摘要。

它的前提是你已经知道什么叫正确。如果目标含糊、需要权衡或要求高度打磨，只因为任务数量多就选择 Luna，可能得到大量整齐但方向错误的结果。

## 16.3 一张实用选择表

| 任务特点 | 优先考虑 | 原因 |
| --- | --- | --- |
| 目标含糊、价值高、需要判断和打磨 | Sol | 适合复杂开放任务 |
| 日常多步骤工作、调查、审查和执行 | Terra | 平衡能力与效率 |
| 规则稳定、批量提取、分类和转换 | Luna | 适合清晰可重复工作 |
| 需要近实时文字或代码迭代 | Codex-Spark | 独立的低延迟模型，能力边界更窄 |

这张表只是起点。真实效果还受提示、上下文、工具、推理强度和验收标准影响。不要把模型名称当成质量保证。

## 16.4 用四个问题选择模型

### 一、任务有多模糊

如果连最终结构和路线都需要模型帮助决定，优先选择更擅长开放推理的模型。规则已经写清楚时，可以选择更高效的模型。

### 二、错误代价有多高

面向客户的正式材料、重要决策支持和复杂修改值得使用更强模型，并配合更严格验证。临时整理和可轻易重跑的任务可以先追求效率。

### 三、任务是否可以批量验证

提取、分类和转换通常有固定字段或样例，适合高容量模型。需要品味、取舍或解释的任务较难机械验收，更依赖综合能力。

### 四、真正瓶颈在哪里

如果时间花在下载、渲染、运行测试或等待网站，换快模型未必明显加速。如果问题来自缺少资料，换更强模型也不能补齐事实。

## 16.5 不要过早进行模型优化

大多数人可以从默认设置开始。先用一个熟悉任务观察结果，再决定是否调整。过早在多个模型之间反复切换，会把提示、上下文和模型差异混在一起，难以判断改善来自哪里。

一种可靠方法是建立自己的小型基准任务：选择三到五项经常重复的真实工作，为每项准备输入、理想输出和检查表。比较模型时保持提示、材料和验收方式一致，再记录质量、耗时和使用量。

模型评估不应只看第一段文字是否漂亮，还要检查：

- 是否正确使用了全部关键材料；
- 是否遵守边界；
- 是否完成了要求的工具步骤；
- 是否留下可以复核的证据；
- 修改成本是否真的更低。

## 16.6 当前模型会变化

模型名称、默认设置、可用套餐和推荐方式都可能更新。因此，本书把选择原则放在正文，把当前型号放在带日期的版本说明中。

使用时应查看当前模型选择器和官方文档。账号方案、组织管理员、登录方式以及使用 ChatGPT 还是 API key，都会影响模型可用性。API 中存在某个模型，不代表它一定出现在桌面应用；反过来也一样。

旧模型还可能被弃用。官方资料显示，使用 ChatGPT 登录 Codex 时，`gpt-5.2` 和 `gpt-5.3-codex` 已被弃用；依赖旧名称的配置或脚本应按当前文档更新。通过 API key 使用时，则要以 API 模型页面为准。

## 16.7 其他模型与自定义提供方

Codex 还可以连接支持相应 API 的其他模型或提供方。这属于进阶配置，不意味着任意模型都能完整支持 Codex 的工具使用、上下文规模和交互体验。

选择非默认模型前，应确认：是否支持需要的工具调用、上下文和输出；认证与计费属于哪个系统；数据经过哪些服务；出现问题时由谁提供支持。不要只因为模型能返回文本，就假设所有功能都等价。

对普通读者，优先使用官方推荐模型和默认配置通常更稳妥。只有在成本、合规、本地部署或特定能力确实有要求时，才值得增加提供方配置的复杂度。

## 16.8 一个工作流可以使用多个模型

复杂工作不一定从头到尾使用同一模型。可以让高效模型完成资料扫描、字段提取和初步分类，再由更擅长判断的模型综合结论、处理矛盾并打磨正式成果。

例如，一项调研可以由 Luna 处理规则清楚的标签，Terra 检查异常和整理证据，Sol 完成最终判断与报告。但这种分工只有在任务量足够大、阶段边界清楚时才有价值。小任务频繁切换模型，协调成本可能超过节省的时间。

多模型流程还需要统一输出格式和验收标准。前一阶段如果丢失来源或过度压缩，后面的强模型也无法恢复证据。主任务应记录每个阶段使用了什么输入、产生什么输出、由谁完成最终检查。

如果无法清楚划分阶段，就先使用一个合适的默认模型完成全流程，等真实瓶颈出现以后再拆分。简单而可检查的流程通常比理论上最省资源的复杂路由更可靠。

## 16.9 常见误区

**永远选择最强模型。** 简单重复任务可能因此更慢、更贵，却没有可见收益。

**模型快就代表任务完成快。** 工具、网络、文件渲染和人工确认也会占用时间。

**模型能弥补缺失上下文。** 更强的推理只能更好地处理现有信息，不能可靠创造缺失事实。

**一次体验代表模型水平。** 输出具有波动，应使用多项真实任务和固定检查方式比较。

**模型决定一切。** 清晰目标、相关材料、合理权限和实际验证，常常比换模型更能改善结果。

## 16.10 第一次实践：建立自己的模型选择卡

选择三个日常任务：一个开放任务、一个常规多步骤任务、一个规则明确的批量任务。为它们分别写下：

1. 最终成果；
2. 输入材料；
3. 最大允许错误；
4. 验收方法；
5. 更看重质量、速度还是使用量。

然后让 Codex 先提出模型建议：

> 根据任务的模糊程度、错误代价、批量规模和验收方式，为这三个任务选择合适的模型。说明理由和备选方案，不要假设更强模型一定更好。

在你可用的模型中实际完成一项小测试，记录结果。你的选择卡应来自自己的工作证据，而不是只抄一张通用排行榜。

## 16.11 本章小结

模型选择是在能力、效率和任务风险之间匹配。Sol 更适合复杂开放工作，Terra 适合日常多步骤任务，Luna 适合清晰、重复、可批量检查的工作。

从默认模型开始，用真实任务和统一验收标准比较。先解决目标与上下文问题，再考虑模型优化。

> 最好的模型不是名字最响亮的模型，而是以合理代价稳定完成当前任务的模型。
