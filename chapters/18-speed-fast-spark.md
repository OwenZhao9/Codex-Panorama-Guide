# 第十八章：速度——Standard、Fast 与 Codex-Spark

等待 AI 完成任务时，人们最容易产生一个直觉：越快越好。但一项工作真正花费的时间，既包括模型思考，也包括读取文件、搜索网页、运行工具、生成成果、等待权限和执行检查。

Codex 中的 Standard、Fast 与 Codex-Spark 都和速度有关，却不是同一种选择。理解它们的差别，才能避免用更高成本换来并不明显的收益。

## 18.1 先分清三种“快”

### Standard 与 Fast

Standard 和 Fast 是服务速度选项。Fast 让受支持的模型以更高速度运行，同时消耗更多 credits。模型本身没有因此变成另一个模型，推理强度也不会自动改变。

### Codex-Spark

Codex-Spark 是一个独立模型，不是速度开关。它为接近实时的文本和代码迭代优化，延迟很低，但整体能力比主要模型更窄，并有自己的使用限制。

### 降低推理强度

把 High 调到 Medium 也可能更快，但这是减少本次任务的推理投入。它可能改变结果的分析深度，与 Fast 加速同一个设置不是一回事。

因此，看到“慢”时先问：是模型计算慢、推理投入高，还是工具与环境耗时？

## 18.2 Standard 模式

Standard 是普通运行方式，适合多数工作。它不需要额外速度倍率，也便于观察一个模型在常规成本下的实际表现。

以下情况优先使用 Standard：

- 任务并不紧急；
- 主要耗时来自文件、网页、测试或人工确认；
- 需要长时间运行，使用量比等待时间更重要；
- 正在比较模型或推理等级，希望先建立稳定基线；
- 批量任务可以在后台完成。

Standard 不代表低质量。质量主要取决于模型、推理强度、上下文和验证。它只是没有购买额外的服务速度。

## 18.3 Fast 模式的当前规则

截至 2026 年 7 月 18 日，Fast 可把受支持模型的速度提高约 1.5 倍，并以更高倍率消耗 ChatGPT credits。

| 模型 | 相对 Standard 速度 | 当前 credits 倍率 |
| --- | --- | --- |
| GPT-5.6 | 约 1.5 倍 | 2.5 倍 |
| GPT-5.5 | 约 1.5 倍 | 2.5 倍 |
| GPT-5.4 | 约 1.5 倍 | 2 倍 |

这些是会变化的产品规则，使用前应查看当前官方页面和界面提示。Fast 目前面向使用 ChatGPT 登录的桌面应用、Codex CLI 和 IDE Extension；CLI 可以使用 `/fast on`、`/fast off` 和 `/fast status` 管理当前状态。

如果使用 API key，Codex 按 API token 计费，不使用 ChatGPT credits 倍率。API Priority processing 有自己的价格规则，不能与 ChatGPT Fast 简单等同。

## 18.4 什么时候 Fast 值得使用

Fast 的价值取决于“等待时间是否真的重要”。适合的情况包括：

- 你正在与模型快速来回迭代；
- 每次响应都阻塞下一步人工工作；
- 任务使用受支持模型，模型推理占总时间的大部分；
- 截止时间紧，额外 credits 可以接受；
- 需要在会议或现场演示中降低等待。

不太值得的情况包括：

- 一项任务会在后台运行，你并不等待；
- 大部分时间用于下载、编译、测试或渲染；
- 流程需要频繁等待人工审批；
- 大批量任务对成本非常敏感；
- 任务本身没有明确目标，速度只会更快地产生返工。

可以先运行一次 Standard，观察总时间构成，再决定是否开启 Fast。没有基线，就很难知道额外消耗换来了什么。

## 18.5 Codex-Spark 是什么

截至当前版本，GPT-5.3-Codex-Spark 是面向 ChatGPT Pro 用户的研究预览模型。它针对接近即时、纯文本的代码和日常迭代优化，适合延迟比综合能力更重要的场景。

Spark 与 Fast 的差别非常重要：

| 对比 | Fast | Codex-Spark |
| --- | --- | --- |
| 本质 | 加速受支持模型的服务模式 | 独立模型 |
| 能力 | 保留所选模型的定位 | 更快但能力范围较窄 |
| 使用限制 | 更高 credits 倍率 | 自己的预览资格和限额 |
| 适用 | 想加速 Sol、Terra 等任务 | 需要近实时文本或代码迭代 |

如果任务需要复杂规划、广泛工具、多来源研究或高质量成品，不应只因为 Spark 快就默认选择它。可以用 Spark 快速探索和小幅修改，再把重要审查交给更全面的模型。

## 18.6 怎样优化任务的总时间

真正的总时间大致由几部分组成：

> 总时间 = 理解与推理 + 工具执行 + 外部等待 + 验证 + 人工确认

Fast 主要改善第一部分。要缩短完整流程，还可以：

- 提供准确文件和清晰目标，减少反复澄清；
- 把相互独立的调查适度并行；
- 对规则清楚的子任务使用更高效模型；
- 避免重复读取无关资料；
- 提前说明审批点，不要在最后才发现不能发布；
- 为测试、渲染和网络步骤设置合适范围；
- 只在关键阶段要求完整验证。

速度优化不能以删除必要检查为代价。一个两分钟生成、两小时返工的结果，比十分钟生成、一次通过的结果更慢。

## 18.7 速度与使用量怎样取舍

可以把任务分为三类。

**互动型任务**：你必须看完结果才能继续，例如现场写作和交互式调试。速度价值高，可以考虑 Fast 或 Spark。

**后台型任务**：例如大规模资料整理和夜间检查。等待不阻塞人，优先 Standard 和高效模型。

**高价值型任务**：错误代价远大于等待，例如正式决策材料。先选合适模型与验证，再考虑是否用 Fast 缩短等待。

团队还可以设定简单预算规则：Fast 只用于互动阻塞的任务；批处理默认 Standard；Spark 只处理能力边界明确、结果容易检查的工作。

切换速度设置前，最好回答四个问题：这次任务是否正在阻塞人？所选模型是否支持 Fast？总时间里模型计算占多少？额外 credits 是否比节省的时间更有价值？如果四项都没有清楚答案，先使用 Standard 建立一次基线。

速度设置也应在交接中写明。否则团队看到任务消耗突然上升，可能不知道是工作量变化还是开启了 Fast。对于自动化和批处理，定期检查默认模式，避免一次临时加速变成长期高倍率消耗。

对个人用户也是如此：把 Fast 当成有明确收益时才开启的工具，而不是默认的“更好按钮”，通常更容易控制使用量。

任务结束后及时恢复 Standard，可以避免下一项并不紧急的工作沿用高倍率设置。

## 18.8 常见误区

**Fast 会降低推理强度。** Fast 是服务速度，推理等级需要单独设置。

**Fast 一定让总任务快 1.5 倍。** 如果工具和外部等待占大部分，总时间提升会小于模型速度提升。

**Spark 就是开启 Fast。** Spark 是独立、能力较窄的模型。

**最快设置最省钱。** Fast 以更高 credits 倍率换速度；Spark 也有独立限额。

**任务慢说明模型不够快。** 模糊目标、无关上下文和反复返工常常才是真正瓶颈。

## 18.9 第一次实践：测量而不是猜测

选择一个需要一到三分钟、容易重复的小任务。固定模型、推理强度、提示和输入，分别使用 Standard 与 Fast 运行一次：

> 阅读这三份材料，生成一张包含主题、关键结论、来源和不确定项的表格。不要改动原文件。完成后说明读取、分析、生成和检查各花费了哪些步骤。

记录总等待时间、结果质量、工具步骤和 credits 消耗。不要用两次结果的措辞差异判断速度效果，只检查是否都达到同一验收标准。

如果 Fast 明显减少了你必须等待的时间，再把它用于类似互动任务；如果差异主要被文件处理掩盖，就保持 Standard。

## 18.10 本章小结

Standard 是默认服务方式；Fast 以更高 credits 消耗加快受支持模型；Codex-Spark 是独立的低延迟、能力较窄模型；降低推理强度则是减少本次分析投入。

> 先找到时间花在哪里，再决定为哪一种速度付费。
