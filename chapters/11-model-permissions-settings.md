# 第十一章：模型、权限与基础设置

Codex 提供模型、推理强度、速度、权限、个性、记忆、网络和配置文件等大量选项。第一次看到这些设置，最容易犯的错误不是“少配置”，而是还没有真实需求就同时修改十几项，最后无法判断哪一项造成了变化。

基础设置的目标是建立一套稳定起点：模型使用当前推荐默认，推理强度匹配日常任务，权限限制在工作区，越界时由人确认。等真实任务出现瓶颈，再一次调整一个因素。

## 11.1 先分清设置改变什么

常见设置可以分为五层：

| 设置层 | 主要作用 |
| --- | --- |
| 模型与推理 | 决定基础能力和本次分析投入 |
| 速度与使用量 | 决定服务速度及相应额度消耗 |
| 权限与网络 | 决定文件、命令和外部资源边界 |
| 个性与指令 | 决定表达方式和长期工作规范 |
| 客户端偏好 | 决定通知、主题、终端和界面行为 |

这些层不能互相替代。选择更强模型不会获得更多文件权限；Full access 不会让推理更正确；改变 personality 只影响沟通方式，不会提升能力；Fast 加快服务，不会自动减少推理步骤。

出现问题时先确定属于哪一层。回答太浅可能需要更好任务或更高推理；文件打不开属于环境或权限；工具无法联网属于网络；措辞不合适才可能是个性与指令。

## 11.2 模型先使用推荐默认

模型名称和可用范围会变化，因此本章不把某个型号写成永久默认。当前 Codex 会根据登录方式、方案和客户端提供推荐模型；普通读者先使用产品默认，通常比手工锁定旧模型更容易维护。

需要选择时，依据任务而不是排行榜：复杂开放问题使用综合能力更强的模型；日常多步骤工作选择平衡型；规则清楚、批量可检查的工作可以选择高效率模型。第 16 章会完整讨论当前 Sol、Terra、Luna 和其他模型定位。

API 模型列表与 ChatGPT 客户端模型选择器并不完全等价。使用 ChatGPT 登录时，以当前账号可见选项为准；使用 API key 时，以 API 组织与项目可用模型为准。

不要在项目配置中无理由固定型号。模型更新或弃用后，旧配置会让任务失败或错过推荐默认。只有评估、兼容、成本或团队一致性确有要求时，才固定并记录核对日期。

## 11.3 推理强度怎样设为默认

推理强度决定模型在一次任务中投入多少分析。日常起点可以使用 Medium；格式转换、简单提取等清楚任务可降低；复杂诊断、重要审查和多条件规划再提高。

桌面与 IDE 可能显示 Light、Medium、High、Extra High 等名称；CLI 配置常使用 `low`、`medium`、`high`、`xhigh` 等值。实际支持等级取决于模型和客户端。

不要把所有任务固定到最高。更高强度通常等待更久、使用更多额度，也无法弥补缺少材料和错误目标。先用可验收任务观察，只有结果反复遗漏关键关系时才升级。

计划模式还可以使用独立推理默认，但入门阶段不必配置。先让执行与计划都使用产品推荐设置，等复杂规划确实需要更深分析再区分。

## 11.4 速度模式不是质量模式

Standard 是普通服务方式；Fast 在受支持模型上用更高 credits 消耗换取更快返回；Codex-Spark 则是独立的低延迟模型。具体倍率和资格会变化，第 18 章提供带日期快照。

基础设置保持 Standard。只有模型响应正阻塞人工交互、且额外消耗值得时临时开启 Fast；任务结束后恢复。后台批处理、长测试和网络等待通常不会因为 Fast 获得同等总时长改善。

## 11.5 权限模式的三个常见选择

本地 Codex 的权限菜单可能包括：

**Ask for approval**：Codex 在工作区边界内行动，需要越界时暂停让你确认。它是多数工作和入门任务的推荐起点。

**Approve for me / Auto-review**：符合条件的越界请求交给自动审查代理。它不会扩大沙箱，但会减少人工批准。用于稳定长任务前，应先理解审查范围和失败行为。

**Full access**：移除重要沙箱限制，允许更广文件和网络操作。它不应是默认设置，只适合外部环境已经隔离、任务确需完全访问且风险可接受的情况。

管理员要求可能禁用某些模式。菜单里看不到 Full access 不是故障，也不应通过修改本地文件绕过组织政策。

## 11.6 沙箱与审批要一起看

沙箱定义技术边界，例如哪些文件可读写、命令能否联网；审批定义越过边界时由谁决定。改变审批者不会改变沙箱本身。

在传统配置中，常见沙箱模式是：

- `read-only`：检查文件，写入受限；
- `workspace-write`：可以在工作区修改并运行常规命令；
- `danger-full-access`：没有文件与网络沙箱限制。

常见审批策略是 `untrusted`、`on-request` 和 `never`。适合本地日常工作的组合是 `workspace-write` 加 `on-request`；完全访问通常意味着 `danger-full-access` 与 `never`，风险明显更高。

新版 permission profiles 可以把文件系统和网络规则组合成命名配置，目前处于 Beta。它与旧 `sandbox_mode` 配置不能混用。普通读者优先使用界面权限模式，不要同时维护两套机制。

## 11.7 图形界面中的基础设置

桌面应用设置适合管理日常偏好：通知、主题、键盘、是否防止长任务时休眠、跟进消息行为、Browser、Computer Use、个性、记忆和归档对话。

其中只有少数会改变智能体实际边界。Browser 和 Computer Use 涉及工具与系统权限；Memories 影响可用长期上下文；Permissions 决定可选择模式。主题、字体和 personality 主要影响界面与表达。

个性可以选择 Friendly、Pragmatic 或 None，它不会改变模型能力。Custom instructions 适合个人跨任务偏好；项目必须遵守的规则仍应写进项目 `AGENTS.md`，不要只依赖个人设置。

## 11.8 `config.toml` 在哪里

CLI、IDE Extension 和桌面 Codex 共享主要本地配置。个人默认通常位于：

```text
~/.codex/config.toml
```

可信项目可以在仓库内添加：

```text
.codex/config.toml
```

Codex 会从项目根向当前目录加载项目配置，离当前目录更近的项目层可以覆盖上层同名值。出于安全原因，未被信任项目的 `.codex` 配置、Hooks 和项目规则不会加载。

项目配置应保存可以由团队共享的项目行为，不应重定向个人认证、供应商或机器级遥测。个人密钥和账号配置不应提交到仓库。

## 11.9 一份最小本地配置

没有必要创建包含所有选项的配置文件。下面只表达一种常见安全起点：

```toml
model_reasoning_effort = "medium"
sandbox_mode = "workspace-write"
approval_policy = "on-request"
```

这里故意不固定模型，让客户端使用当前推荐值。也没有开放网络、额外目录或 Full access。

如果界面已经满足需要，甚至不必手工写这三行。配置文件更适合希望 CLI、IDE 与桌面保持同一持久默认的用户。修改前备份现有文件，每次只改一项，重新启动相关客户端并用同一练习任务验证。

## 11.10 临时覆盖与持久默认

一次任务的特殊要求不一定要写进全局配置。CLI 可以通过专用参数或 `--config` 为单次运行覆盖值，例如临时选择模型或工作目录。

选择规则可以是：

- 当前对话的目标和边界：写在提示；
- 一次运行的技术选项：使用界面或 CLI 临时覆盖；
- 个人跨项目默认：写入用户 `config.toml` 或个人指令；
- 团队项目设置：写入可信项目 `.codex/config.toml`；
- 项目工作规范：写入 `AGENTS.md`；
- 组织强制约束：由管理员配置 requirements。

把所有内容塞进一个文件会让范围混乱。尤其不要用个人设置替代团队规则，也不要让项目仓库控制本机认证。

## 11.11 网络与搜索基础设置

本地命令网络、Web Search、Browser、Chrome、插件和云端网络是不同通道。开启网页搜索不等于让终端可以下载依赖，允许某个 Browser 网站也不等于本地命令获得全网访问。

在需要最新公开信息时使用实时搜索，并要求来源与日期；本地命令只开放任务必要域名。项目配置中的网络规则要明确，而不是使用“允许所有”解决一个依赖下载问题。

网络故障排查时记录具体通道：搜索没有结果、Browser 被阻止、终端网络关闭，还是云端代理无法访问。不同通道要在相应设置中处理。

## 11.12 怎样避免配置失控

配置复杂度本身会成为故障来源。常见问题包括：旧模型名、多个层重复设置、项目覆盖个人默认、CLI 单次参数没有记录、同时使用新 permission profile 与旧 sandbox 配置，以及从网上复制不理解的 Hooks 或 MCP。

维护时遵循四条规则：

1. 从默认开始，只为真实问题增加配置；
2. 一次改变一个变量，用固定任务比较；
3. 给动态选项记录日期和原因；
4. 定期删除不再需要的例外。

出现难以解释的行为时，先查看加载了哪些配置层和当前客户端版本。`codex doctor` 可以帮助生成诊断信息，但分享报告前要检查敏感数据。

## 11.13 第一次设置实践

先记录当前基线：模型、推理强度、权限模式、工作目录和网络状态。用同一小任务运行一次，再只改变推理强度或权限中的一项。

> 读取当前项目 README，生成一份结构摘要。不要修改文件，不要联网。完成后说明实际使用的模型、推理等级、权限边界和工具；列出因权限未完成的步骤，不要申请 Full access。

比较变化是否符合预期。推理等级调整不应改变文件权限；只读权限也不应让模型停止解释内容。确认理解后，再把稳定选择设为持久默认。

## 11.14 常见误区

**把模型锁定后结果更稳定。** 旧型号会变化或弃用，稳定性还依赖提示、材料和验证。

**Auto-review 等于更大权限。** 它改变审批处理者，不扩大沙箱。

**Full access 能解决所有失败。** 环境缺失和错误目标不会因此修复，风险却会扩大。

**Personality 会提高智能。** 它只改变沟通风格。

**配置越多越专业。** 最小、可解释、经过测试的配置更可靠。

## 11.15 本章小结

基础设置应从当前推荐模型、Medium 推理、Standard 速度、工作区写入和按需审批开始。界面管理日常偏好，`config.toml` 保存持久技术默认，`AGENTS.md` 保存项目规则，管理员要求负责组织约束。

> 好设置不是开放最多能力，而是每一项改变都能说清原因、范围和验证方法。

下一章将深入安全与隐私：为什么沙箱只是基础，还需要防范提示注入、凭证泄露和不可逆行动。
