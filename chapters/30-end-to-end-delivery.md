# 第三十章：从需求到交付的完整链路

你收到一句任务：“下周管理层要看用户研究，帮我准备一下。”如果立刻让 Codex 写报告，它很可能快速生成一份结构完整、却不一定解决真实问题的材料。受众想决定什么？使用哪一批访谈？数据截至哪天？交付的是报告、演示还是口头提纲？谁负责最后确认？

可靠交付不是“提示—生成”两步，而是一条从需求澄清到成果验收的闭环。Codex 可以参与每一环，但人必须在目标、风险和最终采用上承担责任。

> 任务的单位不是一条提示，而是一个能够被定义、执行、验证和交付的结果。

## 30.1 完整链路的八个阶段

一项可复用的 Codex 工作流可以分为八个阶段：

1. 定义结果；
2. 建立上下文；
3. 盘点材料与权限；
4. 规划步骤与检查点；
5. 执行并记录进度；
6. 验证内容和成果；
7. 交付、审查与决定；
8. 复盘并沉淀方法。

简单任务可以快速走完，复杂任务则要把阶段显式写出来。阶段的价值不是增加文档，而是让错误更早暴露：目标错了，在执行前修正；材料缺了，在分析前补齐；输出不合格，在发布前发现。

## 30.2 第一阶段：把活动改写成结果

“研究市场”“整理资料”“优化项目”描述的是活动，不是完成状态。先回答三个问题：谁会使用成果？使用它做什么决定？最终必须看到什么？

例如：

> 为周一的管理层会议制作一份不超过十页的用户研究演示，帮助决定下季度优先解决哪三个问题。使用本季度 20 份访谈和当前满意度调查；每项建议说明证据、影响范围与未知项。

这里包含受众、用途、格式、范围和完成条件。Codex 不必猜“准备一下”是什么意思。

目标仍然模糊时，先在 Chat 或计划模式中讨论，不要开始创建正式文件。让 Codex 反问：“哪些决定会因为这份成果而改变？什么内容即使正确也不属于本次范围？”

## 30.3 第二阶段：建立正确上下文

上下文只应包含会改变结果的信息：项目背景、术语、受众、历史决定、当前版本和不能违背的规则。

把相关工作放进同一 Project，让多个任务共享文件和指令；但为不同成果建立独立对话。项目提供长期背景，对话保持单一结果。必须持续遵守的项目规范写进 `AGENTS.md` 或项目文档，不要只依赖一段旧聊天。

开始时让 Codex 用自己的话复述：目标是什么、受众是谁、已知限制有哪些、还缺什么。复述不是为了礼貌，而是捕捉理解偏差。

上下文也不能无限增加。把几十份“也许有用”的材料塞进任务，会淹没关键证据。需要探索的大量日志或搜索结果可以放在独立子任务，主任务只保留摘要、来源和决定。

## 30.4 第三阶段：盘点材料、版本与权限

在执行前建立材料清单：文件名、来源、日期、版本、用途和可读状态。区分原始资料、加工数据、参考样例和最终成果。

要求 Codex 报告实际读取成功、失败和跳过的材料。一个文件打不开时，不能在最终报告里假装它已经被覆盖。时间敏感内容要记录数据截止日；同名“最终版”要确认哪一个生效。

权限与材料一起设计。只读研究不需要修改原件；创建报告只需写入交付目录；联网只允许必要来源；对外发送应留到人工审查之后。

可以在任务开头写：

> 先只读盘点材料和可用工具。列出无法访问、重复或版本冲突的来源，不要开始写正式成果。说明完成任务所需的最小文件、网络和外部操作权限。

## 30.5 第四阶段：决定是否先规划

步骤短、风险低、验收清楚的任务可以直接执行。涉及多个成果、多个来源、不可逆行动或前后依赖时，应先进入计划模式。

一个有效计划至少包含：

- 最终成果与不做事项；
- 输入材料与缺口；
- 阶段和先后依赖；
- 每阶段的可见产物；
- 验证方法与人工确认点；
- 失败后的恢复方案。

不要把“搜索—分析—写作—完成”当作计划，它没有说明每阶段怎样判断正确。更好的检查点是：“完成来源清单后先确认范围”“完成数据表后核对总数”“形成建议前先列矛盾证据”“发布前只保存候选版本”。

计划确认后再转执行。需求变化时更新计划和完成标准，不要让旧步骤继续自动推进。

## 30.6 第五阶段：让执行保持可观察

Codex 开始工作后，不需要逐条指挥，但应保留能够改变方向的可见信息：当前阶段、已完成成果、遇到的阻塞、下一步和需要决定的问题。

低风险任务可以连续完成；重要任务在检查点停下。运行中发现关键材料错误，应使用 steer 立即纠偏；只是希望下一轮补充一个独立任务，则排入 queue。

进度报告应围绕成果，而不是只说“正在分析”。例如：“已读取 18/20 份访谈，两份 PDF 无文字层；完成主题标签，等待确认是否进行 OCR。”这样的状态能让人做决定。

不要让中间文件散落。使用 `drafts`、`deliverables` 和明确版本名；代码项目保留 Git diff；外部系统写入记录对象、时间和结果。执行过程越长，越需要一份当前事实来源。

## 30.7 第六阶段：验证不是最后读一遍

不同成果需要不同证据。

| 成果 | 主要验证 |
| --- | --- |
| 研究报告 | 结论可追溯、来源时效、矛盾与未知项 |
| 表格 | 行数、类型、公式、总计、异常与抽样 |
| 演示 | 内容逻辑、数字一致、页面溢出和实际预览 |
| 网站 | 链接、布局、交互、权限、数据保存与真实访问 |
| 项目修改 | diff、测试、格式、回归和安全审查 |
| 自动化 | 手动试跑、无变化、失败、重复执行和停止条件 |

先做机器可执行检查，再做内容抽样与人工判断。Codex 可以运行检查并报告证据，但“我已核验”不是证据本身。要求给出来源位置、测试命令、退出状态、截图、预览或差异。

验证还要覆盖负面情况：材料为空会怎样？来源冲突会怎样？同一任务运行两次会怎样？权限不足时会报告还是猜测？

## 30.8 第七阶段：交付一个决策包

交付不只是把文件路径发给用户。一份完整交付通常包含：

1. 最终成果在哪里；
2. 做了哪些关键改变；
3. 使用了哪些来源与数据截止日；
4. 运行了哪些验证；
5. 仍有哪些未知、失败或限制；
6. 哪些行动尚未执行；
7. 接收者下一步需要决定什么。

例如：

> 已在 `deliverables/research-deck.pptx` 生成 9 页演示。结论来自 18 份可读访谈和调查表 v3，数据截至 7 月 15 日；两份扫描 PDF 未纳入。已检查页面预览、数字与来源映射。尚未发送或发布。请确认第二条建议是否保留，再生成最终版本。

这比“已经完成，请查收”更容易审阅和承担责任。

## 30.9 第八阶段：复盘并沉淀

任务完成后记录三个问题：哪里最耗时？Codex 反复犯了什么错？哪条临时要求以后应该复用？

一次性的修正留在任务里；项目长期规则更新 `AGENTS.md`；可重复方法整理成 Skill；固定命令做成 Action；稳定且低风险的流程再考虑 Scheduled。

不要把第一次成功就自动化。至少在不同输入下多次运行，确认来源变化、空数据、权限失败和重复执行都有安全行为。

复盘还应清理临时文件、worktree、连接、token 和过期规则。流程沉淀的目标是减少下一次工作，不是积累更多无人理解的配置。

## 30.10 怎样处理需求变化

真实项目很少一次说清。需求变化时先判断属于哪一类：补充细节、改变范围、改变最终成果，还是推翻原目标。

小调整可以在当前任务 steer；改变完成标准时要更新计划和验收；完全不同成果应新建任务，避免旧上下文干扰。

记录被替换的决定。例如预算从十万元改为八万元，明确旧数字不再使用，并检查所有表格、报告和演示是否同步。不能只在聊天最后补一句新要求，就假设早期文件自动更新。

## 30.11 一个完整示例

任务：根据客户反馈准备产品优先级建议。

**定义**：给产品负责人一份五页报告，用于选择下季度三项优先改进。

**上下文**：当前产品目标、不可改变的合规要求、已决定不做的功能。

**材料**：访谈、支持工单导出、调查表，均记录截止日期和可读状态。

**计划**：先清单与清洗，再主题归类，再证据核验，最后报告；建议形成前停下确认分类。

**执行**：Work 负责资料和报告，子任务分别分析访谈与工单，主任务统一口径。

**验证**：每条建议至少有两类证据；抽查原文；数字与表格一致；未知项单列。

**交付**：报告、来源映射、验证记录和待决定项，不自动发送。

**沉淀**：把分类字段和验收表整理成下次可复用 Skill。

## 30.12 常见误区

**提示写得很长就等于需求清楚。** 长文字也可能没有受众、结果和完成条件。

**计划确认后不能改变。** 计划服务于目标，证据变化时应更新。

**执行过程越透明越好。** 关键状态应该可见，但无需把全部日志塞回主上下文。

**测试通过就可以交付。** 还要检查需求、内容、风险和未验证项。

**成功一次就适合自动化。** 稳定流程需要多种输入和失败场景验证。

## 30.13 第一次实践：完成一个小闭环

选择三份非敏感资料，使用下面的任务：

> 为项目负责人制作一页状态摘要。先确认受众、资料范围和数据截止时间；盘点实际可读文件并提出计划。摘要包含进展、决定、风险、下一步与未知项，每条注明来源。不要修改原文件，不要发送。完成后抽查来源、检查每个下一步是否有负责人和日期，并交付成果位置、验证证据和未完成事项。

验收时不要只看摘要内容，还要检查八个阶段是否都留下必要证据。能完整跑通小任务，才适合把方法用于更长项目。

## 30.14 本章小结

从需求到交付的完整链路是：定义结果、建立上下文、盘点材料与权限、规划、执行、验证、交付和复盘。Codex 可以提高每个阶段的速度，但阶段之间的责任不能被一句“帮我全部做完”消除。

> 好的智能体工作流，不是让 AI 一口气跑得最远，而是让每一步都朝同一个可验证结果前进。

下一章将放大这条链路，讨论复杂、长时间和可以并行的任务怎样拆解与持续推进。
