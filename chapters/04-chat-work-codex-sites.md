# 第四章：Chat、Work、Codex 与 Sites

同样一句“帮我做一份产品比较”，可以有四种完全不同的期待：你可能只想听一个比较思路，也可能希望 AI 读完文件并交付报告；你可能要修改一个软件项目，也可能最终想发布一个可以访问的网站。

Chat、Work、Codex 与 Sites 不是简单的能力高低排序，而是四种不同工作入口。选错入口，AI 仍可能给出结果，但过程会更别扭：只需要一句解释却启动了复杂任务，或明明想要完整文件，却一直停留在聊天建议。

> 先看你要交付什么，再选择工作方式。

## 4.1 四种入口的核心区别

截至 2026 年 7 月 18 日，可以先用这张表建立直觉：

| 入口 | 最适合的目标 | 典型成果 |
| --- | --- | --- |
| Chat | 问答、讨论、构思和短草稿 | 一个答案、一段文字、一组建议 |
| Work | 完成有明确结果的日常工作 | 报告、表格、演示、分析、持续更新 |
| Codex | 使用项目和开发工具完成技术或文件工作 | 文件修改、代码、测试、差异、项目成果 |
| Sites | 创建、托管、迭代和分享在线体验 | 网站、Web 应用、游戏及生产链接 |

这四者有重叠。Work 与 Codex 使用同一套核心智能体能力，Codex 也能完成研究和文档；Sites 背后同样可能涉及项目文件和代码。区别主要在界面、默认表达方式、可见工具和交付路径。

因此，不必担心一开始做出“永远不能更改”的选择。先进入最贴近当前成果的模式，需求变大或变得更技术化时再切换。

## 4.2 Chat：先想清楚，或者只要一个答案

Chat 适合低门槛的对话型工作：解释概念、搜索公开信息、头脑风暴、比较选择、改写文字、总结一段内容或澄清需求。

例如：

> 用不超过三百字解释用户留存率，并给一个生活化例子。

> 我在“成本低”和“交付快”之间犹豫，请帮我列出需要考虑的五个问题。

> 把这段通知改得更友好，不改变日期和行动要求。

这些任务的成果就是回答本身。你不需要 AI 建立项目、运行脚本或创建复杂交付物。

Chat 也适合作为大型任务的前厅。目标还不明确时，可以先讨论受众、范围和输出，再转入 Work 或 Codex。这样比带着一句模糊想法直接让智能体执行更稳妥。

Chat 不适合承担你明确需要多来源、多个步骤和完整文件的任务。它可以给出报告草稿，但如果你真正需要 AI 读取资料、创建文档并持续修改，Work 更贴合结果。

## 4.3 Work：把结果委派出去

Work 模式面向“请完成一项工作”，而不只是“请回答一个问题”。它可以使用文件、插件和获准工具，检索信息、创建交付物、运行流程，并把成果推进到可以审阅的状态。

适合 Work 的任务通常具有几个特征：

- 有清楚的最终成果；
- 需要多个来源、工具或步骤；
- 手工完成需要明显时间；
- 输出需要继续查看、修改或复用；
- 任务可能定期更新或持续推进。

例如：

> 阅读这六份会议材料，制作一份不超过十页的决策演示。区分已决定、待决定和风险，每项注明来源；不要发送，完成后检查每页是否有溢出和空白内容。

在 Work 中，你可以查看进展、回答澄清问题、改变方向，并在重要行动前审批。桌面环境允许时，它还能使用本地文件、应用和浏览器。

Work 的重点是完成成果，而不是展示所有技术细节。你通常更关心报告是否可用、表格是否正确，而不是它执行了哪些底层命令。

## 4.4 Codex：看见项目和执行细节

Codex 适合需要项目环境、文件修改、终端、Git、测试和技术差异的工作。典型任务包括理解代码库、修复问题、实现功能、审查分支、运行测试，也包括需要精确控制本地文件和工具的非编程工作。

例如：

> 检查这个网站项目，找出手机端导航遮挡正文的原因。先复现，再做最小修改；保持桌面布局不变，运行现有测试并提供 diff，不要提交或推送。

Codex 界面会呈现更多开发细节，例如当前项目、工作树、终端输出、文件差异和审查。对不写代码的读者，这些并不是必须立即掌握的障碍；它们代表工作过程更加透明和可追踪。

Work 与 Codex 并不是两个完全不同的大脑。官方文档说明，它们使用相同的智能体，能力存在重叠。你可以继续在 Codex 中做研究、文档和演示；选择 Work，主要是获得更面向日常工作的表达和界面。

只想快速问一个问题时，Codex 中也可能提供 Quick chat。它帮助你在项目环境附近进行解释和讨论，但不应与完整项目任务混为一谈。

## 4.5 Sites：交付一个可以访问的在线产品

Sites 的目标不是生成一段网页代码，而是创建、托管、迭代和分享一个真实在线体验。它可以从提示或兼容项目开始，制作网站、Web 应用和游戏，并管理版本、部署、访问范围、分析和需要时的数据存储。

适合 Sites 的任务包括：

- 品牌或活动网站；
- 可以填写和筛选的内部工具；
- 带持久数据的小型应用；
- 互动演示、计算器或游戏；
- 把兼容的本地项目发布为托管站点。

例如：

> 创建一个供团队提交内容选题的网站。用户可以填写标题、目标受众和截止日期，列表能够按状态筛选，记录在刷新后仍然保留。先保存一个可审阅版本，不要公开部署。

截至核对日期，Sites 处于 public beta，可用范围和限制可能随方案、地区和工作区变化。还要特别注意：每个 Sites deployment URL 都是生产部署。如果只想检查候选版本，应先保存版本而不部署。

Sites 也不是所有网站项目的唯一选择。需要复杂基础设施、特定云服务或完整工程控制时，更适合先在 Codex 中开发和测试，再使用适合项目的部署系统。

## 4.6 Browser 等工具不等于模式

Browser、Chrome、Computer Use、插件和网络搜索经常与四种入口一起出现，但它们是工具或连接能力，不是同一层级的工作模式。

Work 可以调用 Browser 查资料，Codex 可以用 Browser 检查网页，Sites 可以创建需要预览的站点。工具决定智能体能接触什么，模式决定你怎样组织任务和接收成果。

这一区分很重要。你不应该因为任务要查网页，就默认它属于 Browser；先决定最终要答案、报告、项目修改还是网站，再为对应模式提供所需工具。

## 4.7 怎样在四者之间选择

可以按下面顺序判断：

### 第一个问题：成果只是回答吗

如果只需要解释、建议、短改写或讨论，选择 Chat。

### 第二个问题：需要完整日常工作成果吗

如果要读取多份材料、调用连接数据、生成报告、表格或演示，选择 Work。

### 第三个问题：任务依赖项目、终端或 Git 吗

如果要精确修改文件、运行命令、审查差异或处理软件项目，选择 Codex。

### 第四个问题：最终成果是一个托管在线体验吗

如果希望创建并管理网站或 Web 应用，考虑 Sites。若项目复杂，可以先在 Codex 完成工程工作，再进入 Sites 或其他部署流程。

还可以用一句简短判断：

> 想要回答，用 Chat；想要成品，用 Work；想要项目控制，用 Codex；想要上线网站，用 Sites。

这句话是入门口诀，不是绝对边界。真正选择仍要结合材料位置、工具、权限和账号可用性。

## 4.8 四种入口怎样组合

一项真实工作常常跨越多个入口。

例如发布一份行业专题：先在 Chat 中澄清受众和问题；在 Work 中研究资料、制作报告和演示；需要互动展示时用 Sites 创建专题站；如果站点出现复杂问题，再进入 Codex 查看项目和测试。

组合时要明确交接物。Chat 的讨论应沉淀为目标和约束；Work 的研究应保留来源；Sites 应使用经过确认的内容；Codex 修改后要提供差异和验证。不要只说“沿用之前的东西”，却没有确认新任务是否真的能访问之前的上下文和文件。

对于同一长期项目，可以把相关任务和材料放在同一个 Project 中，但独立工作仍应分成不同任务，避免研究日志、网站调试和最终文案互相污染。

## 4.9 一个可复制的选择练习

把下面四项工作分别分配入口，并说明理由：

1. 解释什么是净推荐值；
2. 根据十份访谈制作一份研究报告；
3. 修复报告生成脚本中的日期错误；
4. 把研究结果制作成可公开访问的互动网页。

然后让 ChatGPT 检查你的选择：

> 分析这四项任务分别适合 Chat、Work、Codex 还是 Sites。对每项说明最终成果、需要的材料和主要验收方法。如果两个入口都可用，指出首选和备选，不要把 Browser 或插件误当作工作模式。

合理答案通常是 Chat、Work、Codex、Sites，但真正学习点在理由：任务二如果只想讨论报告结构，也可以先用 Chat；任务四如果网站需要复杂工程，可能先在 Codex 完成，再进入发布流程。

## 4.10 常见误区

**Work 比 Chat 更聪明。** 两者主要区别是任务形态和执行方式，不是简单智力等级。

**Codex 只能写代码。** 它也能处理研究和文件，只是界面展示更多项目与技术细节。

**Sites 生成预览就不会公开。** 每个部署 URL 都是生产部署；候选版本应先保存而不部署。

**需要网页就选择 Browser。** Browser 是工具，先根据最终成果选择模式。

**选定入口后不能更换。** 真实项目可以按阶段组合，但需要明确上下文和交接成果。

## 4.11 本章小结

Chat 面向答案和讨论，Work 面向可审阅的日常工作成果，Codex 面向项目、文件和开发工具，Sites 面向托管在线体验。它们不是相互排斥的能力等级，而是不同的任务入口。

> 选择入口时，不要先问“哪个最强”，而要问“我最后要检查和使用的成果是什么”。
